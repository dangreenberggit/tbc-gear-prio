### Verdict summary

Of the ~40 files in `packages/core/src` (excluding `proto/*`, `fixtures/*`), exactly **4 files** import Node built-ins directly: `content-hash.ts` and `seams/sim-runner.ts` (both trivially swappable — only `node:crypto`'s `createHash`, used for one hash function each), `seams/cli-sim-runner.ts` (the process-spawning adapter — meant to be replaced, not ported), and `seams/store.ts` (contains both `SqliteStore`, Node-bound, and `MemoryStore`, already pure). `cli.ts` is Node-bound by design (it's the CLI entry point). Every other file — including the entire `rank.ts` orchestrator, all 8 pipeline stages' logic, the gem solver, the set-bonus math, the cap math, and `view.ts` — is pure TS with zero Node imports.

## 3. The execute stage & SimRunner

`packages/core/src/seams/sim-runner.ts` defines the port:

```ts
export interface SimRunner {
  version(): Promise<string>;
  run(req: RaidSimRequest, opts: SimRunOpts): Promise<SimObservation>;
}
export type SimRunOpts = { seed: number; iterations: number };
export type SimObservation = {
  dps: number;
  stdev: number;
  iterationsDone: number;
  simVersion: string;
};
```

`RaidSimRequest` is typed as `Readonly<Record<string, unknown>>` — "opaque protojson ... until §8.1 generated types land" per the file's own comment, meaning the engine does not require the caller's sim to speak any particular concrete TS type beyond a JSON-shaped protojson object.

**Request mutation / seed injection.** `compose.ts` builds the request from a skeleton (deletes `simOptions`/`requestId`, sets `raid.parties[0].players[0].{name,race,equipment}`). Seed/iteration injection happens **after** hashing, inside the concrete adapter — `CliSimRunner.run()` spreads `{ ...req, simOptions: { iterations, randomSeed: String(seed), debugFirstIteration: false } }` right before spawning. This split is load-bearing (PLAN.md §7/R6, `content-hash.ts` comment): the cache key is computed from the pre-injection request, so seed/iterations must be injected by the adapter, not by `compose`/`rank.ts`. A browser adapter must replicate exactly this: accept the un-injected `req`, add `simOptions` itself, then call into the wasm sim.

**Caching.** `simCacheKey(req, simVersion, opts)` = `sha256(stableStringify(req)) + ":" + simVersion + ":" + seed + ":" + iterations`. `RecordedSimRunner` is a `Map`-backed replay adapter keyed by this. This is the pattern a browser "cache to avoid re-simming" layer would reuse, minus the `node:crypto` swap noted in §1.

**What `rank.ts`'s execute stage needs from `Deps.sim`:** (inferred from `rank.ts` imports/usage of `simCacheKey`, `RaidSimRequest`, `SimObservation`, `SimRunOpts`, `SimRunner` — did not trace every call site line-by-line in the 1778-line file, but the shape is exactly the two-method interface above.) It calls `.version()` once to stamp `simVersion` on results/hash, and `.run(req, {seed, iterations})` once per (candidate item × seed) combination — up to `|simmed| × |seeds| + 1` calls per PLAN.md §4's documented cost model, where `|simmed|` is the pool after the rank-time EP prefilter.

**What a wowsims-in-page wasm adapter needs to provide:** an object satisfying `SimRunner` — `version(): Promise<string>` (can likely be a static string from the wasm build) and `run(req, opts): Promise<SimObservation>` that (a) accepts a protojson-shaped `RaidSimRequest` object, (b) injects `simOptions` with the given seed/iterations itself (matching `CliSimRunner`'s injection-after-hash pattern so caching stays correct), (c) invokes the in-page wasm sim (likely via the wasm module's existing JS bindings, since wowsims TBC's web UI already runs sims client-side), and (d) returns `{ dps, stdev, iterationsDone, simVersion }` parsed from whatever the wasm call returns — `CliSimRunner`'s `RawSimResult` parsing (`raidMetrics.dps.avg/stdev`, `iterationsDone`, `error.type !== "ErrorOutcomeNone"`) is a template for the expected response shape, since wowsims' wasm and CLI both go through the same Go sim core and same protojson `RaidSimResult` message.

## 4. resolve/extract/normalize stages & GearSource

Could not open `stages/` as a directory — PLAN.md §5.1 names `stages/resolve, extract, normalize, compose, pool, generate, execute, rank` as a planned layout, but the actual repo has no `packages/core/src/stages/` directory; the stage logic lives inlined inside `rank.ts` (1778 lines) rather than as separate stage files. This is worth flagging as a **drift from PLAN.md's stated file layout** — did not verify whether this was a deliberate later refactor documented elsewhere (e.g. an ADR), so treat as unconfirmed drift, not a bug.

From reading `rank.ts`'s imports and `spec.ts`/`gear-source.ts`/`logged-gear.ts` directly, here is what each named stage does and whether it survives a switch to wowsims' own `Player`/`ItemSpec` proto gear source instead of WCL:

- **Resolve** (find a fight for a character via WCL): **becomes unnecessary.** This stage exists purely to locate _which_ WCL fight to read gear from (`GearSource.findFights`). If gear comes directly from the site's live `Player` object, there is no fight to resolve — the player's current gear _is_ the input.
- **Extract** (read raw WCL gear/talents/buffs for that fight — `GearSource.readGear` → `LoggedGear`): **becomes unnecessary** in its WCL-specific form. But its _output shape need_ doesn't disappear — the engine still needs an equipment vector, and if the wowsims UI already holds a `Player` with resolved `EquippedItem`s (protobuf `ItemSpec` per PLAN.md's own vocabulary), this stage is replaced by a same-page read, not a network call. Talent tree points (`talentPointsByTree`) also become unnecessary as a _classifier input_, since the UI already knows the player's chosen spec directly (no plurality-guessing needed).
- **Normalize** — converting `LoggedGear` (WCL sim-slot-named items) into the 17-slot equipment vector `compose` expects (`logged-gear.ts: equipmentFromLoggedGear`), plus deciding whether a worn item takes an enchant/gems before synthesizing anything (`items.ts`'s `enchantable`/`sockets` fields), plus **spec classification** (`spec.ts: classifySpec`, `matchesRequestedSpec`) and **plausibility checks** (`plausibility.ts`): **mostly still needed, but the sub-parts split differently.**
  - **19→17 slot mapping** (`slots.ts`): **not needed** if wowsims' `Player` object already stores gear in its own 17ish-slot sim-native representation (protobuf `ItemSpec[]` array) rather than a 19-slot armory-style layout. This mapping exists specifically to bridge WCL's 19-slot convention (which includes shirt/tabard) down to the sim's 17. If the source is already sim-native, the bridge is dead code for the browser path.
  - **Spec classification** (`spec.ts`): **not needed** — the wowsims UI already has the player's chosen spec as first-class state (it's a spec-specific tool, e.g. "Retribution Paladin" tab), unlike WCL which has no spec label at all. This whole module (talent-tree plurality, feral form-uptime disambiguation) exists solely to work around WCL's missing spec field.
  - **Plausibility checks** (`plausibility.ts`): **still valuable, orthogonal to gear source.** These are sanity checks on the _finished ranking_ (dead slots, set-bonus confounds), not on how gear was read — keep regardless of `GearSource` implementation.
  - **Enchant/socket "can this slot carry X" checks** (`items.ts` fields, `enchants.ts: enchantAppliesToItem`): **still needed.** This is about item metadata, independent of where the equipped-gear snapshot came from.
- **Compose** (`compose.ts`): **still needed as-is.** Patches skeleton with name/race/equipment regardless of gear source — pure and source-agnostic already.
- **Pool/Generate** (candidate universe filtering, per-item swap generation): **still needed as-is** — orthogonal to where the player's _current_ gear came from.
- **Execute/Rank**: **still needed as-is** — orthogonal to gear source.

**Net effect:** switching `GearSource` from WCL to "read the site's own `Player` object" collapses Resolve and (most of) Extract entirely, and strips the spec-classification and 19→17-slot-mapping sub-parts out of Normalize, but Normalize's item-metadata gating, Compose, Pool, Generate, Execute, and Rank all survive untouched. This is consistent with PLAN.md's own claim that these are "steps," not modules with independent value — most of the WCL-specific steps are steps whose entire reason for existing is WCL's specific poverty of information (no spec field, no race field, 19-slot layout), which a same-page `Player` object doesn't have.

## 5. Proto types

`packages/core/src/proto/*.ts` (11 files: `api_pb.ts`, `apl_pb.ts`, `common_pb.ts`, `db_pb.ts`, `druid_pb.ts`, `hunter_pb.ts`, `mage_pb.ts`, `paladin_pb.ts`, `priest_pb.ts`, `rogue_pb.ts`, `shaman_pb.ts`, `spell_pb.ts`, `test_pb.ts`, `ui_pb.ts`, `warlock_pb.ts`, `warrior_pb.ts`) are **generated by `protoc-gen-es v2.13.0`** — confirmed by the header comment `// @generated by protoc-gen-es v2.13.0 with parameter "target=ts,import_extension=js"` in `common_pb.ts`. They import from `@bufbuild/protobuf` (the sole runtime dependency listed in `packages/core/package.json`) — this is **protobuf-es**, a pure-TS/JS protobuf runtime with no Node-specific code, fully browser-compatible (it's designed for exactly this: isomorphic use in both Node and browser bundlers).

**Alignment with wowsims' own generated protos:** wowsims TBC's web UI is itself written against protobuf-es-generated types from the _same_ `.proto` source family (PLAN.md's own text confirms the `.proto` files are "pinned .proto files from the wowsims release," `vendor/wowsims/proto` per §5.1's tree). Since both `packages/core` and the wowsims UI presumably generate from the same/compatible `.proto` schema at pinned commits, the generated message _shapes_ should match structurally (same field names, same `proto.Stat`/`proto.GemColor`/`proto.ItemSlot` enums, e.g. `common_pb.ts`'s `Stat`, `GemColor`, `ItemSlot` enums are visible in the decoded descriptor). Whether the **exact same package instance** could be shared (avoiding duplicate `@bufbuild/protobuf` message classes in one bundle) depends on whether both projects pin the same protoc-gen-es major version and whether message identity matters for any `instanceof` checks — did not verify this by reading wowsims UI source, so flagging as **unconfirmed**: this needs a check against the actual wowsims TBC repo's proto-generation setup before assuming a clean shared-dependency win versus "two independently generated copies of the same shapes, which just happen to be structurally compatible JSON."

So **yes, ret has phase-3 (and phase-4, phase-5) pool coverage**, and BiS tags **do exist at every phase**, but the BiS-tagged subset is small (15 items) and — per `docs/verification-log.md` line ~143 — **"Ret's curated gear sets are `preraid`, `p1` and `p2` and stop there"**, meaning the BiS _tags_ likely don't extend meaningfully past p2 even though the _pool_ does; this needs cross-checking against which specific items carry the tag at which phase, which I did not do (flagging as unconfirmed detail — the count of 15 was constant across all four files, consistent with tags being sourced from a p2-only curated set that then rides along unchanged in every later-phase universe file, but I did not diff the actual tagged item IDs across files to confirm they're identical row-for-row).
- **Preset/skeleton/EP-weights data (needed to actually _run_ a sim) exist only at p2** for ret: `data/presets/ret/p2.ep-weights.json` (300 B), `p2.individual-sim-settings.json` (7,001 B), `p2.raid-sim-skeleton.json` (25,745 B). Whether that's intentional (talents/APL assumed stable across phases) or a known gap wasn't stated in the files I read — flagging as unconfirmed intent, confirmed as fact from the file listing.

**Feral:**

- Preset data: `data/presets/feral/p1.ep-weights.json` (1,306 B — named p1 because, per a `cli.ts` code comment, "upstream ships no p2 [EP weights] one for it"), `p2.raid-sim-skeleton.json` (39,008 B), `buff-defaults.json` (1,354 B). So feral's sim-runnable data is a **mismatched pair**: p1 EP weights + p2 skeleton, both used regardless of the universe file's actual max phase.

**`ret/` and `feral/` dirs under `packages/core/src`:** grepped and globbed — **neither directory exists** under `packages/core/src`. ## 7. CLI/app entry points

**`cli.ts`** (`packages/core/src/cli.ts`, 576 lines) is the sole entry point in this repo today — there is no `apps/` directory (checked; PLAN.md §5.1 plans one, `apps/web`, but it does not exist in the current tree). `cli.ts`:

1. Parses argv into `RankInput`-shaped fields plus `ViewOptions` plus offline/report flags.
2. Loads four data sources from disk via `readFileSync`/`loadJson`: `data/wowsims.lock.json` (default max phase), `data/presets/{spec}/p2.raid-sim-skeleton.json` (skeleton), `data/presets/{spec}/{p1|p2}.ep-weights.json` (EP weights), `data/universes/{spec}-p{maxPhase}.json` (pool, via `loadUniversePool`/`poolFromUniverse`).
3. Builds `Deps`: `{ gear: new RecordedGearSource(gearData), sim: new CliSimRunner(binary), store: new MemoryStore(clock), clock, raidSimSkeleton: skeleton, epWeights, pool }`. (Live WCL path is explicitly not wired: `if (!args.offline) { console.error("live WCL path is not wired yet..."); return 2; }` — so today's CLI **only** runs in offline/recorded mode.)
4. Calls `rankUpgrades(input, deps, onProgress)`, then `applyView(ranking, args.view)` for terminal/report output.

**The wiring a browser host must replicate:** build the same four-part `Deps` object — `gear` (a `GearSource` reading the page's live `Player`/gear state instead of `RecordedGearSource`'s fixture `Map`), `sim` (a wasm-backed `SimRunner` instead of `CliSimRunner`'s spawn), `store` (`MemoryStore` as-is, or an IndexedDB-backed adapter for persistence across page loads), `clock` (`() => new Date()`, trivial), `raidSimSkeleton`/`epWeights`/`pool` (bundle the same committed JSON as static imports rather than `readFileSync`). Then call `rankUpgrades(input, deps, onProgress)` exactly as `cli.ts` does — `rank.ts`'s public interface is already the entire contract; nothing about it assumes a terminal or a filesystem.

No `apps/` directory and no other CLI/entry-point file was found (`packages/core/src/cli.ts` is the only file with a `main()`/`process.argv` pattern).
