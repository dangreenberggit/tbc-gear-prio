# Upgrades-tab scope — which open tickets block a finished tab

This index categorizes every open ticket (`Status: open|blocked|claimed` in
`.scratch/carry-forward/issues/`) by whether it stands between us and a
**finished wowsims Upgrades tab**. The ticket schema has no field for tab-scope;
this doc fills that gap. It is a judgment layer, not an edit to any ticket.

Every row carries a **Transport** tag saying which of the tab's two transports
the ticket bears on:

- **web** — only the browser/WASM build (the vite page, `lib.wasm`).
- **desktop** — only the packaged `wowsimtbc` binary and its HTTP runner.
- **both** — tab behaviour regardless of which transport serves it.
- **n/a** — no bearing on the tab's runtime at all (pipeline, docs, process,
  test infrastructure).

## Definition of done

A finished wowsims Upgrades tab is judged against four observable conditions.
Each is a command or an artifact a reader can check, not a reading of intent:

1. **Every tab-surface ticket is closed.** The MISSING and STALE loops under
   `## Maintenance` print nothing, and no ticket in **Tab-blocking** remains
   open.
2. **Both transports are gated.** The tab is proven to run, and to produce the
   same ranking within noise, on the web WASM build and on the packaged
   `wowsimtbc` desktop binary, with a scripted check a later session can re-run.
3. **Both pins sit on post-merge upstream `master`.** The engine lock and the
   fork lock name a `master` sha at or after the commit that merged
   `feature/backend-reforge`, and `sync_wowsims.py --check` exits 0.
4. **A PLAN.md §14 box set exists for the tab**, with a
   `docs/verification-log.md` entry recording the evidence for each box.

ADR-0027 (accepted 2026-08-22) settles which front end this is about: the
**wowsims Upgrades tab is the primary product**; the standalone web shell is
secondary and "merges as built... no further Stage 3 work is scheduled." The tab
reads gear **off the page** and sims **in the visitor's browser**
(`docs/plans/wowsims-tab/plan.md` D3/D5); it does **not** use the live WCL
`GearSource`. Consequently ADR-0027 §consequence 3 states ticket 267 (live WCL
gear) is **"not on the critical path"** for the tab, and the standalone-shell /
live-WCL / deploy tickets sit in **Out-of-scope**, each with a one-line note
saying they belong to the shell track ADR-0027 parked.

## The dual-repo split

Every row is tagged by which codebase its fix lives in:

- **core** — `packages/core/**`, `scripts/**`, `data/**`: the ranking engine,
  pipeline, and committed artifacts (this checkout).
- **fork** — `vendor/tbc-new-fork/**` (gitignored; its own git repo): the
  wowsims fork that renders the tab. The tab's code is
  `ui/features/upgrades/` — `components/` and `hooks/` (the React UI) and
  `model/` (run state, views, adapters, and the ranking engine twins under
  `model/engine/`).
- **both** — a ranking-correctness fix in `packages/core` that has a **verbatim
  ported twin** under the fork's `ui/features/upgrades/model/engine/`; the fix
  must land in both copies (port-drift ladder, tab plan §3). The twin is named
  where relevant.
- **tooling** — CI, gates, process, `.scratch` tracker plumbing.

## Categories

- **Tab-blocking** — a finished tab is wrong, incomplete, or not shippable until
  this is fixed. Strict test: a user of the finished tab hits it, or the tab's
  stated §12 scope requires it.
- **Awaiting owner sign-off** — the fix has landed and rendered; the ticket stays
  open only because an owner or SME judgment call has not been recorded.
- **Tab-adjacent** — improves/hardens the tab or its inputs, but the tab is
  shippable without it (polish, defence-in-depth, follow-up, gate coverage that
  does not change tab behaviour).
- **Out-of-scope** — unrelated to the tab (standalone shell, deploy, pipeline
  internals with no candidate-set effect, tooling/process, backlog).

Rows are ranked most-tab-critical first within each bucket.

## Maintenance

This doc is regenerated in the same commit that changes any ticket's `Status:`
line. A ticket that opens, closes, or moves bucket without a matching edit here
makes this index wrong, and nothing else catches it. This doc is also
re-checked at the merge of every chunk of
`.scratch/plans/upgrades-tab-finish-line.md`.

Two loops check it. Run them in Git Bash from the repo root. `pnpm issues:open`
lists only `open`, `claimed` and `blocked` tickets
(`scripts/check_merge_ready.py`), so a `resolved` or `closed` ticket must have
no row. `.scratch/open-ids.txt` is a scratch file; any gitignored path works.

```
corepack pnpm -s issues:open | grep -o 'issues/[0-9]*' | cut -d/ -f2 | sort -u > .scratch/open-ids.txt
for n in $(cat .scratch/open-ids.txt); do grep -q "^| $n " docs/upgrades-tab-scope.md || echo MISSING $n; done
for n in $(grep -o '^| [0-9]* ' docs/upgrades-tab-scope.md | grep -o '[0-9]*' | sort -u); do grep -qx $n .scratch/open-ids.txt || echo "STALE $n ($(grep -m1 -o '^Status: *[a-z]*' .scratch/carry-forward/issues/$n-*.md | awk '{print $2}'))"; done
```

Both loops must print nothing: MISSING names an open ticket with no row, and
STALE names a row whose ticket is not open.

## Judgment calls

The placements a reviewer should scrutinize first:

1. **The whole "going-live-on-GearSource" flag → Out-of-scope (267, 271, 31,
   32, 268).** **ADR-0027** makes the tab primary and states ticket 267 is "not
   on the critical path" because the tab reads gear off the page. I resolved the
   inclusive-vs-strict ambiguity by categorizing under the tab's plan (slices
   1–6 + §12 surface) and parking the live-WCL/deploy tickets Out-of-scope with
   an explicit "stricter reading → blocking" note on 267. If the owner's real
   goal is "both front ends ship," these five move up.

2. **The "Awaiting owner sign-off" bucket holds 254 and 311.** Each has a
   landed fix and an unrecorded owner or SME judgment, so it is a decision
   owed, not code owed. 313, 315 and 330 left it on 2026-10-11: the owner
   signed them off on 2026-09-18 (`4f1e99c5`) and they are now closed.

3. **331 vs 335 vs the set-bonus cluster.** 331 is a confirmed correctness bug
   but lives only in `weightedSetPotentialDps`, called only from the core report,
   not ported into the fork twin and never read by the tab → Out-of-scope for
   the tab. 336 is the live tab-surface half of the same story (a reachable 4pc
   is never disclosed) → blocking. The line: a wrong number or an owner-reported
   broken control on the tab is blocking; a wrong number on a core-only report
   path the tab never reads is out-of-scope.

4. **259 (feral Idol missing) → Tab-adjacent, not blocking.** A feral tab user
   genuinely sees only the worn idol in the ranged slot. Kept adjacent because
   it is `Blocks: phase-2`, that gate is already closed with the caveat
   disclosed, and the tab is shippable for feral with a documented coverage
   limit. Same logic for 89, 43, 293.

5. **269 (`hideOwned`) → Tab-adjacent.** The tab never sets `hideOwned`
   (`model/results_view.ts:115` passes only `withSetPotential` to `applyView`),
   routing around the trap. So the `view.ts`
   drop is a loaded gun in the shared twin, not a live tab bug. Reversible: if a
   future tab change sets `hideOwned:true`, this re-lifts to blocking.

6. **241 (unvalidated skeleton) — Tab-adjacent, and the single hardest call.**
   The skeleton drives every ranking the tab shows, and the ticket names a
   mana/int-valuation concern that could "knock out real upgrades." But the
   displacement question is **explicitly unmeasured**, and the owner ruled on the
   acceptance bar rather than a fix. Placed adjacent because it is an open
   investigation, not a known-wrong number.

7. **376 → Tab-blocking, and 364/366 → adjacent, though all three are engine
   or server code.** 376's `routes.ts` allow-list gates which specs the tab can
   request at all — a user of a finished tab on any of the nine newer specs hits

   real defects in fork engine code the tab runs, but the first moves a number
   rather than breaking a surface, and the second needs a malformed request to

   the 311 family.
