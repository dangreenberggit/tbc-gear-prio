# Upgrades-tab scope — which open tickets block a finished tab

This index categorizes every open ticket (`Status: open|blocked|claimed` in
`.scratch/carry-forward/issues/`) by whether it stands between us and a
**finished wowsims Upgrades tab**. The ticket schema has no field for tab-scope;
this doc fills that gap. It is a judgment layer, not an edit to any ticket.

## Definition of done

"A finished wowsims Upgrades tab" is judged against two anchors:

1. **PLAN.md Stage 3 — the web shell** reaching its §14 gate (~PLAN.md line 907,
   gate at ~line 903): three routes, job submit/poll, skeleton-then-fill,
   assumptions drawer, **view controls over `applyView`** (§12 — raid filter,
   boss filter, slot grouping, "already have it"/owned greyed, pin BiS),
   **exports and share link**, **wowsims attribution**, and every Stage 1 CLI
   check still green.
2. **The flagged-but-unscoped "going live on `GearSource`" pass** (PLAN.md §5.2
   / the "Flagged, not planned" block at ~line 898): building `WclGearSource`
   and flipping the shell off `--offline`.

### The ambiguity, and how it is resolved here

There are **two front ends for one engine**, and they diverge on the
definition-of-done. **ADR-0027 (accepted 2026-08-22)** settles it: the
**wowsims Upgrades tab is the primary product**; the standalone web shell is
secondary and "merges as built... no further Stage 3 work is scheduled." The tab
reads gear **off the page** and sims **in the visitor's browser**
(`docs/plans/wowsims-tab/plan.md` D3/D5); it does **not** use the live WCL
`GearSource`. Consequently ADR-0027 §consequence 3 states ticket 267 (live WCL
gear) is **"not on the critical path"** for the tab.

This creates the ambiguity the brief asked me to flag: the PLAN.md
"going-live-on-GearSource" flag (anchor 2 above) is a **standalone-shell**
deliverable, and under ADR-0027 it is not on the tab's path at all. I categorize
under the **more inclusive reading** — a "finished tab" is the tab plan's slices
1–6 done plus the §12 view/export/attribution surface working in-browser — and I
place the standalone-shell / live-WCL / deploy tickets in **Out-of-scope**, each
with a one-line note that they belong to the shell track ADR-0027 parked, not the
tab. Where a reader takes the stricter "both front ends must ship" reading, the
Out-of-scope shell rows (267, 271, 268, 31, 32, 175, and the deploy/queue set)
move up to blocking; I flag those rows so that re-reading is cheap.

## The dual-repo split

Every row is tagged by which codebase its fix lives in:

- **core** — `packages/core/**`, `scripts/**`, `data/**`: the ranking engine,
  pipeline, and committed artifacts (this checkout).
- **fork** — `vendor/tbc-new-fork/**` (gitignored, main-checkout-only): the
  wowsims fork that renders the tab (`upgrades_tab.tsx`, the engine twins under
  `.../upgrades/engine/`, the `_upgrades_tab.scss`).
- **both** — a ranking-correctness fix in `packages/core` that has a **verbatim
  ported twin** under the fork's `upgrades/engine/`; the fix must land in both
  copies (port-drift ladder, tab plan §3). The twin is named where relevant.
- **tooling** — CI, gates, process, `.scratch` tracker plumbing.

## Categories

- **Tab-blocking** — a finished tab is wrong, incomplete, or not shippable until
  this is fixed. Strict test: a user of the finished tab hits it, or the tab's
  stated §12 scope requires it.
- **Tab-adjacent** — improves/hardens the tab or its inputs, but the tab is
  shippable without it (polish, defence-in-depth, follow-up, gate coverage that
  does not change tab behaviour).
- **Out-of-scope** — unrelated to the tab (standalone shell, deploy, pipeline
  internals with no candidate-set effect, tooling/process, backlog).

Rows are ranked most-tab-critical first within each bucket.

## Judgment calls

The five (plus) placements a reviewer should scrutinize first:

1. **The whole "going-live-on-GearSource" flag → Out-of-scope (267, 271, 31,
   32, 268).** The brief named this flag as part of the definition-of-done, but
   **ADR-0027** makes the tab primary and states ticket 267 is "not on the
   critical path" because the tab reads gear off the page. I resolved the
   inclusive-vs-strict ambiguity by categorizing under the tab's plan (slices
   1–6 + §12 surface) and parking the live-WCL/deploy tickets Out-of-scope with
   an explicit "stricter reading → blocking" note on 267. If the owner's real
   goal is "both front ends ship," these five move up.

2. **272 (fork lockfile, no Windows binaries) → Tab-blocking.** It is not a
   tab-behaviour bug — it is a build bug. I placed it as blocking because the
   ticket's own measurement says `npm run type-check` and the vite build
   "cannot run at all" on Windows from the committed lockfile, so the tab
   literally cannot be built or shipped from the dev machine. A reviewer who
   scopes "finished tab" to rendered behaviour only would call it adjacent.

3. **331 vs 335 vs 313/330 (the set-bonus cluster) split across buckets.** 331
   is a **confirmed correctness bug** with committed proof (4pc invisible in
   full mode), but re-filed 2026-08-29 to **Out-of-scope**: the defect lives only
   in `weightedSetPotentialDps`, which is called only from the core report
   (`rank-report.ts`), is **not ported into the fork's `upgrades/engine/`** twin
   dir, and is **never read by the tab** (verified — zero fork-ui occurrences of
   the symbol; no report files in the twin dir). The earlier "the tab exposes
   these modes" reasoning was wrong: the tab's only set-potential surface is
   `rankableSetPotential`, already noise-gated in both copies. 313/330/328/312 are
   owner-reported **display/labeling** gaps on the tab's own surface → blocking,
   fork. 315 is "shipped but never observed working" → blocking (the feature
   isn't demonstrably done). 335 is a **noise-floor precision** refinement
   (2pc √2 applied to 4pc) → adjacent. The line I drew: a wrong number or an
   owner-reported broken control on the tab is blocking; a precision tune to the
   gate is adjacent; a wrong number on a **core-only report path the tab never
   reads** is out-of-scope for the tab (331).

4. **259 (feral Idol missing) → Tab-adjacent, not blocking.** A feral tab user
   genuinely sees only the worn idol in the ranged slot — a real gap they hit.
   I kept it adjacent because it is `Blocks: phase-2`, that gate is already
   closed with the caveat disclosed (PLAN.md ~line 883), and the tab is
   "shippable" for feral with a documented coverage limit. The same logic put
   89, 43, 293 (all disclosed pool-coverage gaps) in adjacent. A stricter
   "feral must be complete" reading pulls 259 into blocking.

5. **269 (`hideOwned`) → Tab-adjacent (moved from blocking, round-1 review).**
   Originally placed blocking on the reasoning that the tab's "Already have it"
   control (§12) must implement the greyed-and-kept treatment. But the round-1
   review found the **tab already does this** — it sets `hideOwned:false`
   (`upgrades_tab.tsx:1585-1599`), routing around the trap exactly as the
   standalone shell's `greyOwned` does. So `view.ts hideOwned`-drops is a loaded
   gun in the shared `upgrades/engine/view.ts` twin, not a live tab bug — the
   same latent, both-with-twin character as 320 and 104, which already sit in
   adjacent. Moved there for consistency. Reversible: if a future tab change ever
   sets `hideOwned:true`, this becomes live and re-lifts to blocking.

6. **241 (unvalidated skeleton) — Tab-adjacent, and the single hardest call.**
   The skeleton drives every ranking the tab shows, and the ticket names a
   mana/int-valuation concern that could "knock out real upgrades." That would
   corrupt the tab's ranked list directly — which argues blocking. But the
   displacement question (Q1) is **explicitly unmeasured**, and the owner ruled
   on the acceptance bar rather than a fix, so its true severity for the tab is
   undetermined. I placed it adjacent because it is an open investigation, not a
   known-wrong number; a reviewer who treats "unvalidated load-bearing input" as
   unacceptable-until-proven would move it to blocking.

7. **The set-bonus-correctness twins (86, 119, 236) — Tab-adjacent, not
   blocking, on a benign-today judgment.** Each is a real correctness bug in a
   core path with a verbatim fork twin the tab exercises: 86 mis-scores 8-piece
