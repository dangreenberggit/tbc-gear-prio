## Adversarial

Four findings, all reproduced live by the reviewer against the real parser.

**A1 — `assemble_universe.py:1002`, quest zone silently dropped.** The guard
`if qm and not VENDOR_REP_RE.search(text) and not STANDING_PAREN_RE.search(text)`
scans the **whole** string, not the parenthetical `qm` matched. A row carrying
a genuine quest zone _and_ any rep mention loses the zone. Independently
re-verified in this session:
`'Quest: Foo (Nagrand), also sold by Vendor: Bar (Kurenai Honored)'` →
`[{kind: rep, faction: Kurenai}]`, Nagrand gone, while the same text without
the rep clause correctly yields `{kind: raid, zone: Nagrand}`. Consequence if
reached: `zones_hit` misses `phase_zones` and the item drops out of a universe
with no error — the project's stated worst case. **Latent**: measured across
all 215 distinct `wowheadSourceText` values under `data/`, zero at-risk rows.
Deferred to ticket 70.

**A2 — display-spelling fallback for six uncurated ids. Incorrect; rejected.**
The finding assumed `REP_FACTION_DISPLAY` curates 14 of 20 ids and that six
(922/932/934/967/989/1031) fall back to a CamelCase split that disagrees with
the prose spelling. Checked directly: `rep_faction_names()` returns exactly 14
ids and `set(names) - set(REP_FACTION_DISPLAY)` is **empty** — no id falls
back to the split. The 20-vs-14 confusion is between
`data/faction_ids.json` (20 AtlasLoot faction names) and the proto-modelled
id→display map (14). The data axis reached the same conclusion independently.

**A3 — `check_rep_tables.py` is weaker than its docstring. Confirmed, but the
conclusion is friendlier than stated.** Corrupting a non-proto id does pass
that gate green (probed: `KeepersOfTime` 989 → 1234 gives
`rep tables ok … 95 id-checked`, exit 0), because steps 4 and 5 check
name/id agreement through `_atlasloot_ids_by_key()`, the same map that
produced the id. But the corruption **is** caught — `check_atlasloot_regen.py`
exits 1 with a precise message naming hand-editing as a cause. The two gates
are complementary, not redundant, and `pnpm verify` runs both. The reviewer's
"locally a fresh worktree passes vacuously" caveat is real and already
disclosed in the CI workflow's own comment (the `sync:atlasloot:restore` step
exists for exactly this). Working tree restored and both gates re-run green.

**A4 — `pool-hardening.test.ts:353`, `expect(universeP3.length).toBe(394)`.**
A count assertion over an artifact regenerated by the script under review;
pins the number without witnessing correctness. The named-item assertions
around it are the real coverage. Judgement call, not filed.

Not found: no unhandled `RankError` kinds, no purity violation in
`packages/core/src`, and `source_rep_factions` correctly returns empty for an
unresolved id, so a display string cannot grant phase membership.

  `data/phase_raids.json` (Ashtongue 1012 p3, Scale of the Sands 990 p3, SSO

  carries `phase <= max_phase`, so a Sunwell item behind a BT faction cannot

The axis the user asked for. There is no installed skill for it — none exists
in the Matt Pocock upstream set either, whose nearest neighbours

   is a pure addition of the `factions-tbc.lua` entry — `commit` stays
   `0bc91eb6`, `data-tbc.lua`'s sha256 byte-identical. `do_restore` iterates
   `TRACKED` rather than the lock's file map, so adding an input does not
   require moving the pin.

   `vendor/atlasloot` aside and running all three gates: all exit 0, with
   `rep-tables:check` still doing real work. A fresh offline worktree passes.
   CI compensates via the `sync:atlasloot:restore` step.
3. **Regeneration confined to what the commits claim.** Field-by-field across
   all six universes: entry counts 253→253, 240→240, 381→407, 364→394,
   411→441, 492→534; zero removals; zero top-level key changes; the only
   changed field on surviving entries is `sources`, and every mutation is an
   intended upgrade of an unresolved row.
4. **Determinism holds, and the gate's claim is honest.** `parse_atlasloot.py`
   run twice into separate dirs, `cmp` identical. `check_atlasloot_regen.py`
   compares a fresh parse against `HEAD` — output-matches-input, not run-to-run
   reproducibility — but its docstring claims only the former, so the wording
   is accurate. Determinism is measured today, unguarded going forward.
5. **Lossy normalisation guarded.** `_faction_key` collapses to `[a-z]`; the
   guard at `check_rep_tables.py:138` iterates all 20 names and would fire on
   a collision. Verified 20 names → 20 distinct keys, no collisions; the
   apostrophe cases collapse onto their own entry, which is the intended join.
6. **Single-witness transcription disclosed.** The one hand-entered datum is
   `repFactions` in `data/phase_raids.json`; its note says the names are
   comments and only `factionId` is matched on, which the code confirms.
7. **Stale comments/tests updated with the data.** The wrong belief in
   `pool.ts` was removed; the pool-hardening count moved 364→394 with a
   three-step comment accounting for each delta.
