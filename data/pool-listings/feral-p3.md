# Phase 3 candidate pool — feral

Generated by `python scripts/list_phase_pool.py`; checked by
`pnpm pool-listings:check` in `pnpm verify`. Do not edit by hand — a

## What this listing is for

The pool the Upgrades tab sims comes from this repo's assembled universe.
This listing puts that pool next to a pool derived from the wowsims item
database and explains every difference, so a missing item is visible
instead of silent. Nothing here changes membership: an item the rules
below cannot explain is reported under "Unexplained", never added.

## Precedence

| Field | Primary |
|---|---|
| membership and source metadata | the local universe |
| phase | the wowsims DB — any disagreement fails this listing's gate |
| zone vocabulary | the wowsims DB's own `zones[].name` |
| completeness | the wowsims DB is the reference the universe is audited against |

## Membership rules

**Local membership (U)** is the `entries` of the committed universe
artifact `data/universes/feral-p3.json`, unchanged.

**wowsims-primary membership (W)** is every item in the pinned DB with
`phase <= 3`, `quality == Epic (4)`, and spec-eligible under
the assembler's own `SPEC_PROFILES` — class allowlist, armor type,
weapon and hand rules, relic type. Those rules are imported from
`scripts/assemble_universe.py`, not restated in code here, so the audit
cannot drift from the assembler it audits.

Two quality bounds are deliberate and worth stating because neither is
obvious from the code:

- **Legendary (`quality == 5`) is excluded.** The DB holds
  18 legendaries, 2 of them phase
  3 (Warglaive of Azzinoth 32837, Warglaive of Azzinoth 32838), and none is ret- or
  feral-usable under these same spec rules: they are one-hand sword and
  dagger, ret admits no one-hand weapons, and a druid can use neither
  swords nor daggers. The engine additionally strips the Kael'thas
  temporary legendaries, which `eligible_d7` already screens. Re-run:

  ```bash
  python -c "import json;db=json.load(open('vendor/wowsims/db.json'));print([(i['id'],i['name'],i.get('phase')) for i in db['items'] if i.get('quality')==5])"
  ```

- **Rare and below are excluded from the audit.** The Rare phase-3
  gap measured here is 0 for this spec, so auditing Rare adds
  noise and no finding. This bound is narrower than `eligible_d7` alone,
  whose own floor is `MIN_QUALITY = 3` (Rare) — hence the explicit Epic
  filter on top of it. The figure is recomputed on every regeneration of
  this listing, so it cannot silently go stale.

## Reason categories

Every item in W but not U gets exactly one category. They are tried in
this order, so an item that several rules would reject is reported under
the most specific one:

- **d** — class allowlist excludes this spec's class
- **a** — per-spec weapon/hand/armor exclusion
- **b** — fails the eligible_d7 stat and slot screen
- **c** — stub-only sim effect
- **e1** — drops only outside this phase's zones
- **e2** — sourced, but by a route the local assembly did not admit
- **f** — no recognized source route
- **g** — unexplained

**Categories d, a and b are always zero here, for a structural reason
worth being explicit about.** They name eligibility rules, and W is
*defined* as the items that pass those rules — so no member of W can
fail one. They explain why an item never entered W at all; they cannot
explain why a W-member is missing from the local pool. They stay in the
table at zero so a reader can see they were considered rather than
quietly dropped.

Each of the remaining categories is a test that can fail, which is what
keeps **g** reachable and this listing's zero-unexplained claim worth
something:

- **e1** — the item drops, but only outside this phase's zone list. The
  local assembler admits raid drops by zone, so older content is out of
  scope by design rather than missing by accident.
- **e2** — the item is sourced and never drops at all (crafted, or a
  reputation reward), and the local assembly's route for that kind did
  not admit it. Split from **e1** because "drops outside this phase" is
  simply false about an item that drops nowhere, and the two want
  different follow-up: e1 is working as designed, e2 is a question about
  a local route.
- **f** — the DB records no source at all, so no local route could find
  it.

An item that is sourced, drops inside one of this phase's zones, and is
still absent falls through to **g** and gets read by a person; nothing
absorbs it silently.

The fork clone `vendor/tbc-new-fork` is **not** read, and the distinction
matters. The DB audited here is upstream wowsims' own, pinned by
`data/wowsims.lock.json`; the fork carries its own copy of that file
which is not byte-identical to the pin. The pinned copy is used because
it is the only one that exists in CI — the clone is gitignored and lives
on one machine, so reading it would make these committed bytes depend on
which machine regenerated them, and the byte-compare gate could never
pass in both places. Re-run to compare the two copies:

```bash
python -c "import json;a=json.load(open('vendor/wowsims/db.json'))['items'];b=json.load(open('vendor/tbc-new-fork/assets/database/db.json'))['items'];A={i['id']:i.get('phase') for i in a};B={i['id']:i.get('phase') for i in b};print(len(A),len(B),set(A)^set(B),[k for k in A if A[k]!=B.get(k,A[k])])"
```
