Orchestration observations — the set-bonus arc

10–12 August 2026 · branch feat/set-bonus-value · tickets 90–126 · written for the owner's own review

Summary

Over three days the branch went from "the set-bonus numbers are disputed and nobody has run a simulation" to "every disputed number is measured, one genuine bug in our own code was found and fixed, and the two remaining gaps are named with error bars instead of stories." That was done by roughly three dozen agent runs costing about 4.7 million tokens, of which the largest single block was one ten-iteration diagnostic loop.

What the arc accomplished

  • Measurement replaced argument. The central dispute — the value of the Malorne 2-piece bonus — had a regression camp saying 100–133 DPS and a domain-expert camp saying 15–40, with neither side having run a sim. Direct measurement settled it at 131.1 ± 6.6, in favour of the regression camp, and explained the mechanism (a cat rotation is energy-limited, so an energy proc converts almost entirely into extra Shred casts — +11.3% of them).
  • A real bug in our code, found by ten iterations of falsification. The 103/106 loop killed seven candidate explanations by experiment — gem mangling, dead meta gems, wrong item variants, socket capacity, artifact displacement, a supposed "meta tax", stale fixtures, out-of-range item ids — before finding the actual defect: fillEmptyCandidateGems filled a gem socket that wowsims itself leaves empty, inventing an epic gem the player does not own and inflating a package figure by about 10 DPS. Confirmed at the oracle when the owner's own web export came back carrying an empty socket.
  • Gemming honesty and package display fixed. Auto-fill is now capped at rare quality, the meta-repair step obeys the same cap, package figures ride on member rows per threshold instead of one shared number pretending to be four, and a one-piece-short package now reports "unmeasurable" instead of a fake 0.00.
  • Both specs exercised. Feral was the whole arc's subject; the ret catch-up round closed a standing gap ("ret is still unexercised") by producing the first ret artifact with set context, which immediately found that package display mode was doing nothing at all on that report.

The big cost centres

  1. The 103/106 diagnostic loop — roughly 750k tokens across four director completions plus its ten worker investigations. This was the single most expensive thing in the arc and also the thing that found the only real code defect. It was expensive because it was honest: it kept refusing to accept a story until an experiment killed the alternatives, and it twice retracted a conclusion it had already reported as fact.
  2. The fix round — about 1.0 million tokens across six workers. Five implementation waves and one fresh-context review. The two biggest workers were the per-threshold package work (239k) and the judgment sweep (201k).
  3. Early orchestration — 312k for the tickets 90–99 round alone, the single largest individual run in the arc.

One correction to how those costs were labelled. The rounds run on Fable at low effort were treated in the logs as the cheap workhorse lane, with Opus reserved as the expensive sharp lane. Anthropic's published lineup has it the other way round: Fable is the top tier, above Opus in both capability and list price. So roughly 1.6 million tokens — the Fable directors and their inherited workers — were spent on the most expensive tier while being reasoned about as the economical one. The low effort setting did constrain how hard those runs thought, but it did not make them a cheaper model. See the note on limits below for sources.

The process lessons that mattered most

  1. Run the simulation. Two camps argued for a long time about a number that a few hours of sim time settled definitively — and the winning camp's reasoning was still partly wrong (the proc-mask argument pointed the right way but did not explain the magnitude; energy starvation did). Being right for the wrong reason is not a good position to defend from.
  2. Never price a change across a threshold that moves. A specified measurement recipe was itself confounded and would have produced a confidently negative 4-piece bonus. The general rule that fell out — never price a stat swap across a configuration where the number of active set bonuses changes — would have invalidated three separate runs in this arc.
  3. A safety net that invents a verdict is worse than no net. The two highest-severity bugs the first pre-merge review found were both inside the component added that same round to catch silent confounds, and both survived a 615-test green suite. When a missing warning reads as evidence of health, the failure is invisible.
  4. Green locally is not green on CI. A test depended on a file that existed in the working tree but was gitignored and untracked. Everything passed for everyone who had run the generation step, and would have failed on every fresh checkout. Several tickets had already recorded "verify green" without that qualification.
  5. Verify the reviewer before obeying the reviewer. A review finding is a claim, not an order. In this arc a reviewer correctly caught a factually false code comment, and a separate investigation produced two convincing false bugs out of a broken test harness. Workers that checked first saved retractions; the loop that did not check reported wrong conclusions as fact twice.
  6. Write down what each worker did and what it cost, as you go. The per-worker observability logs are the only reason this document can say anything specific. Where they were not kept — the early rounds, before orchestrator briefs asked for per-child model and token rows — the record is just "inherited" and the detail is gone.

Process observations — the failures

FailureA background worker died silently while its parent waited forever

In the ret catch-up round, the worker responsible for generating the first ret report started its long simulation run in the background and then ended its turn without leaving anything on disk. Its director had armed a monitor to wait for completion — but the monitor was watching a side-channel signal the harness does not track, so the "done" event never fired. The director sat waiting on something that could not arrive.

The run itself had actually succeeded. The work was fine; only the handoff was missing. It took an outside intervention to notice, and the director then had to reconstruct the worker's log from the artifacts it left behind.

The lesson written into the director log: the harness notifies you about children it tracks; a monitor on anything else can wait forever. Verify the worker is alive, or prefer synchronous workers. A manager must not background a worker and end its turn without leaving a handoff on disk.

FailureTwo session-limit kills mid-round

Two orchestrators were killed by the usage limit while a round was in flight. Both were recovered by resuming from the transcript rather than restarting.

  • The ret catch-up director was killed right after the stall above, so the round absorbed two disruptions back to back. It resumed and finished.
  • The fix-round director was killed mid-round with its token spend never reported — the one genuinely missing number in the accounting. It was killed at a fortunate moment: most commits had already landed and the tree was clean, so nothing was half-done. The very next thing it tried to do (a report-regeneration worker) died at spawn on the same limit, spending roughly nothing.

What made the recovery cheap was that the resumed session could re-read the transcript and the commit history, and then verify rather than assume. The fix-round director on resume explicitly re-checked that ticket 118's code change was actually in the tree before continuing, and recorded that check. That is the difference between resuming and guessing.

FailureTwo sessions filing into the same ticket numbering space

Tickets in this repo are markdown files whose names begin with a number, and the number is chosen by picking the next free one. On the morning of the 11th, two sessions were both live: one filed tickets 111 and 112 at 08:29, and the other closed the diagnostic loop and filed ticket 113 at 09:18. The usage log records the near-miss in its own row for that work — the chips ticket is annotated with where it was meant to land versus where it was filed.

Nothing was lost, but the failure mode is obvious: two sessions that both compute "next free number" from a tree that is changing under them will collide, and the collision is a filename collision, which git resolves by whichever write lands second. The related and better-documented hazard from the same period is below.

The record on disk is thin here — the usage log's annotation and the commit timestamps are the evidence; there is no post-mortem of the incident itself.

FailureThe commit hook sweeps files you did not touch

The pre-commit hook runs its formatter against every dirty tracked file, not just the paths named in git add. That means anything another session left modified in the same tree rides along in your commit.

This nearly bit twice. It was anticipated in the ret-catchup plan (which instructs the director to run git status before every commit precisely because the hook sweeps everything), and it produced one real, if benign, incident: commit b3321cd carried a 930-line churn in a handoff document that nobody had edited — the formatter rewriting line endings and re-wrapping paragraphs. The 108 deleted lines were reformatting, not lost text, and that was verified rather than assumed before the commit was accepted.

On Windows this is a standing hazard: CRLF and LF differences make a file look wholly rewritten when nothing meaningful changed, which both hides real edits in noise and makes review diffs useless. The rule that came out of it is in the review-incorporation handoff: run git status before each commit, and if you see changes you did not make, stop and sort it out.

FailureConfident conclusions reported as fact, then withdrawn — twice

The 103/106 loop reported two closing stories that later proved wrong, and both retractions are worth reading because of how they were handled.

  1. "The owner benchmarked a different, better-geared character." A whole set of figures was computed against a settings export the owner later said carried the wrong gear. The conclusion had already been reported as fact. It was withdrawn in full, in place, rather than quietly amended.
  2. "Iteration 3 already priced that at zero." The loop's own log claimed an earlier iteration had ruled out a mechanism. On re-checking, that iteration had never tested it — it had varied which gem filled a socket, never whether the socket was filled at all. The correction is recorded as a correction to the log's own record, naming its earlier self as too generous.

The loop also corrected its own statistics against itself: a later iteration found it had used the wrong standard deviation, and the corrected figures made its open residue harder to dismiss, not easier. The log notes that tightening the error bars cut against its own conclusion, "which is the honest direction."

Process observations — the wins

WinReviews caught things the test suite could not

Every review round in this arc paid for itself, and the findings were of a kind tests structurally cannot catch:

  • A CI-breaking untracked file. The fix-round reviewer found that a test loaded a report artifact that was gitignored and untracked — so pnpm verify was green on the developer's machine and would have failed on every fresh clone, taking eight tests down at collection time. The reviewer reproduced it by moving the file aside rather than asserting it.
  • False comments. A code comment justified a design decision with a claim about gem quality that was simply untrue (all eighteen meta gems are rare, not epic). The reviewer checked it against the data. The same false claim had already been copied into a commit message, which cannot be amended — so it was corrected durably in the ticket instead.
  • Vacuous tests. A test asserting that a quality cap held would have passed whether or not the cap ever ran. It was strengthened with an explicit guard that the repair actually happened first, and made to fail by mutation to prove the strengthening was real.
  • Claims written as present capability that were actually aspirations. A comment and an ADR both said a renderer could name the completing piece. No renderer could, and the reviewer traced all three code paths that return early before ever reaching it.

WinWorkers verified reviewer claims before acting on them

The stance that emerged and was later written down: a review finding is a claim, not an order, and every finding gets exactly one of four dispositions — a fix, a ticket, a wording correction, or a written "accepted as-is, and here is why." None get silently ignored.

In practice this meant the reviewer's own findings were re-checked. Of the fix round's nine findings, five were fixed, three were read and accepted as-is with a recorded reason (a harmless pointer, a cosmetic truncation, and an arithmetic equivalence that had already been verified), and one was independently confirmed before action. That is a healthy ratio: it means the reviewer was mostly right and the implementer was not simply obeying.

WinMeasurement-first discipline, held under pressure

The single most valuable habit in the whole arc: falsify by experiment, not by argument. The 103/106 loop's disposition table is a list of seven plausible-sounding explanations, each with the specific experiment that killed it. None was argued away.

Two supporting habits made the measurements trustworthy:

  • Build the test arms through the real code path. One investigation hand-edited a single gear slot instead of going through the real engine function, and thereby produced two convincing false bugs and about 35 DPS of stats no player could actually have. That mistake is now a written rule.
  • Prove the gate fails, not just that it passes. When a drift check was added, the change it was supposed to catch was deliberately introduced to confirm the check exits with an error, then reverted before commit. The principle behind it — a net that never fires is as bad as one that fabricates — was applied in both directions.

WinPer-worker observability logs

Each round kept a director log with one row per worker: status, commits, its own detailed log file, and — from the fix round onward — its model and token count. Each worker wrote its own numbered log. This is why the arc can be reconstructed at all.

The value shows most clearly by contrast. For the early rounds, where orchestrators were not asked to record per-child model choices, the record says "inherited" and the actual detail is unrecoverable. The usage log itself notes this and states the change in practice: from 2026-08-11 on, orchestrator briefs ask for per-worker model and token rows.

The logs also carried corrections. The 103/106 director log records its withdrawn conclusions in place, with the reason, rather than editing the history to look clean — which is exactly what made the second retraction cheap, because the reader could see the first one coming.

Costs, limits, and pacing

The usage limit was hit twice, both times on the 11th, both times mid-round. The practical effects were these:

  • Work in flight is at risk, work committed is not. Both kills were survivable specifically because the rounds were committing per green slice rather than batching one commit at the end. The fix-round director was killed with a clean tree at a known commit; nothing had to be redone. Had it been holding four workers' output uncommitted, that would have been a very different morning.
  • Resume beats restart, if the record is good enough. Both kills were recovered by resuming from the transcript. What made that work was the on-disk record — director logs, worker logs, commit messages — that let the resumed session verify where it actually was rather than trusting its own recollection. The verification step is not optional; the fix-round director re-derived which commit carried which change before continuing.
  • The limit degrades gracefully at the edges and abruptly in the middle. One dispatch simply died at spawn, spending nothing, which is the cheap failure. The mid-round kill is the expensive one because it leaves a gap in the accounting — the fix-round director's spend is the one number in this whole document that is unrecoverable.
  • Pacing implication. The expensive runs in this arc were Opus-class diagnostic loops running at high effort for long stretches — several individual completions above 200,000 tokens. Those are the runs worth starting early in a window rather than late, and the ones worth checkpointing to disk most aggressively, because they are also the ones whose context is most expensive to reconstruct. Cheap, bounded questions were correctly sent out as separate short-lived subagents rather than absorbed into a long session.

Nothing in this section relies on the specific mechanics of when the limit resets — see the note below.

Note on the mechanics behind those limits

Checked against Anthropic's own documentation on 12 August 2026, so the pacing advice above rests on facts rather than folklore. Anything that could not be confirmed from an official page is marked as such.

The session window. Subscription plans use a session-based limit that resets every five hours, and there is a separate weekly limit that resets at a fixed time each week assigned to your account. How many messages fit in a window varies with message length, attachments, conversation length, and which model and features are used (support.claude.com — What is the Pro plan?). On team and enterprise seats the same shape applies: a per-seat allowance on a rolling five-hour window plus a weekly window (code.claude.com/docs/en/costs). The commonly repeated detail that the five hours start from your first message rather than a clock boundary is consistent across third-party sources but I could not confirm it word-for-word from an official page — treat it as likely but UNVERIFIED. Likewise the exact weekly cadence in hours.

Claude Code shares the pool with everything else. Activity in Claude Code and in Claude chat count against the same limits — there is no separate coding budget (support.claude.com — Using Claude Code with your Pro or Max plan). There is also a distinct, model-specific limit on the top-tier model that can be hit before the general session limit, which is why switching models can sometimes keep you working when the top model is exhausted (code.claude.com/docs/en/costs). That is very likely what the two kills in this arc looked like from the inside.

Subagent tokens are not free. A subagent gets its own separate context window, but its spend counts against the same session and plan totals as the main conversation — it is tracked as an attribution breakdown within one pool, not a second pool. /usage (also /cost, /stats) shows session usage and that per-source breakdown, including subagents (code.claude.com/docs/en/costs). So the 4.7 million tokens in the table above were drawn from the same allowance the sessions themselves were spending, which is the most direct explanation for two limit kills in one day.

Subagents inherit the parent's model by default. Officially, the model field defaults to inherit and uses the same model as the main conversation (code.claude.com/docs/en/sub-agents). That is exactly what the "inherited" rows in the usage table mean, and it is why the fix round's five implementation workers all ran on the director's model with no effort level set — nobody chose that, it was the default. Selection order is: environment variable, then the per-call model parameter, then the subagent's own frontmatter, then inherit.

Effort is a real, settable parameter. In Claude Code it is the /effort command, with a persistent setting available; on the API it is an output-config field with levels low, medium, high (the default), xhigh and max, not all of which every model supports (platform.claude.com — effort). Subagents can override it in frontmatter. Worth noting against the fix round's own log entry, which recorded that effort was "not settable from the dispatch tool" for its reviewer — that was a limitation of how the worker was dispatched, not of the platform.

Model tiers, for reading the table correctly. Anthropic's published lineup puts Fable 5 at the top ("most capable widely released model"), then Opus 5 for complex agentic coding, then Sonnet 5 for the speed-and-intelligence balance, then Haiku 4.5 as the fastest (platform.claude.com — models overview). Fable is a real published model name, not a nickname. This is worth pausing on: the usage log's shorthand treats "Fable (low)" as the cheap-and-cheerful director tier and Opus as the sharp lane, but Fable is officially the more capable and more expensive tier of the two. The rounds run on Fable at low effort were therefore not the economy option they were labelled as.

They are included only for a sense of relative tier cost, and no dollar figure for this arc is stated because none can be honestly derived from what was recorded.
