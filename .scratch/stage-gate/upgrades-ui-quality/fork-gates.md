entry point through `node` directly** rather than through `.bin/` or the
`npm run` script that calls it.

## The `fmt` gate is scoped on purpose

`oxfmt --check ./ui` is red tree-wide and **stays red by design** — 194 files at
our fork tip. Do not read that as a gate failure, and do not try to fix it by
reformatting the tree.

The scoped gate covers the **ten files this project owns**, listed in
`.scratch/stage-gate/tickets-306-308/fmt-owned-files.txt` (paths relative to
`vendor/tbc-new-fork`; read the list from there rather than retyping it). Those
ten were formatted once and the scoped check exits 0, so a future formatting
regression in our own UI code is caught. That matters because **`pnpm verify`
never sees the fork** (`grep -c vendor package.json` → 0), so without this row
nothing at all would cover it.

Why each excluded group is excluded, measured rather than assumed. Both counts
below come from running the check **from inside** its own tree so
`.oxfmtrc.json` resolves — tip 194 failing over 643 files, pristine upstream
base `cbf6b75a889e` 85 failing over 529:

- **Upstream's 85** — inherited redness on a commit we never touched. Upstream's
  own tree is unformatted against its own config; not our fight.
- **`upgrades/engine/**` (34 files)** — byte-gated by
  `scripts/check_engine_port_drift.py` under `pnpm verify` against
  `engine/PROVENANCE.md`. Reformatting stales those hashes. Note this really
  does bite: oxfmt reindents these files from 2-space to tabs, so a stray
  format pass over the engine tree is a large, gate-breaking diff.
- **`upgrades/data/**` (65 files)** — committed **generated** artifacts plus
  their own `PROVENANCE.md`. Hand-reformatting generated bytes produces a
  result no regenerator would reproduce.

That accounts for the whole tip−base difference: 34 + 65 + 10 = 109.

**Verify the invocation form by scan count, not by a config message.** Run from
inside the tree, the base scans **529** files; the wrong by-path form
(`--check <path-to-worktree>/ui` from elsewhere) silently loses the config,
scans **674**, and reports 157. oxfmt 0.62.0 prints no "no config found"
diagnostic, so a string check for one passes on exactly the run it should
reject. The 157 figure that appears in older notes is that artifact.

One standing disagreement worth knowing: `lint:js` warns
`simple-import-sort(imports)` on several of the ten formatted files. oxlint and
oxfmt want different import orders. The warning count is **265 both before and
after** the formatting pass, so this is upstream baseline noise, not something
the scoped gate introduced.

## Why `test:locales` matters here

Adding any new UI string touches three places, per review finding F4:

1. `assets/locales/en/translation.json` — the string itself.
2. `schemas/translation.schema.json` — `additionalProperties: false` plus the
   key listed in `required` at three levels, so an unlisted key fails.
3. The call site in `upgrades_tab.tsx`.

CI runs this at `.github/workflows/run_tests.yml:54`, so skipping it locally
only defers the failure.
