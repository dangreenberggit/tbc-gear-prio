# Plan — 411-desktop-bulk-wallclock

## Goal

When this plan is done, the repo holds a committed, re-runnable measurement of desktop (HTTP / Go-server) bulk screening against the per-candidate loop at cap 40, ret P5, matched accuracy, with the Go finalist stage fixed (sized independently of the response size, still running, its refined results kept), and a keep-or-delete verdict on the bulk-screening substrate that follows from a decision rule written in this plan before any run. Concretely: the fork carries one commit (new `finalist_results` request field, Go merge-back, builder change, an opt-in runner switch the default path never takes, harness timing flags); `data/wowsims-fork.lock.json` pins that commit; `pnpm verify` is green; `pnpm desktop-gate:check` passes (a)–(h) unchanged against the existing golden; `.scratch/stage-gate/411-desktop-bulk-wallclock/measurement.md` records the numbers, the rule and the verdict; ticket 411 is closed with that verdict and ticket 406 points at it.

## Approach

**The fix (403 lever 1, fixed not bypassed).** `topResults` is read twice in `vendor/tbc-new-fork/sim/core/bulk/bulk_sim.go`: at line 186 it sizes the finalist refinement set, at line 197 it truncates the response (C1). The decoupling is a new `int32 finalist_results = 9` field on `BulkSimRequest`. Go reads it as the finalist-set size, falling back to `topResults` when zero, so every upstream caller (which passes 5 for both) behaves exactly as before. Because the stage-ran path of `runBulkSimFinalistStage` returns only the refined finalists (C3) and the client rejects a chunk whose response has fewer rows than candidates (C4), Go must merge the refined finalists back into the full result list before truncating to `topResults`. The builder then sends `topResults: candidates.length` (unchanged, keeps every row) and `finalistResults: 5` — upstream's own display size (`BulkSimDefaultTopResults`), the value the stage was designed for; 1 would make the stage exit at `len(finalists) < 2`, which is a bypass. The stage still runs, over 5 of 25, and its product (the refined means) reaches the response.

**Rejected alternative: Go-only clamp** (`finalists = min(topResults, 5)` with no proto change). Cheaper (no proto regen) but it silently changes semantics for any upstream caller who asks for 10 displayed results, and it hides the decoupling in a constant instead of naming it in the request. A field is the honest divergence to carry.

**Rejected alternative: bypass** (skip the stage when the client reads only `dps`, 403's Track A). Out of scope by the brief; it is what made the route dead.

**Turning bulk on for the measurement only.** Since 403 the tab constructs `WasmSimRunner` unconditionally (C6). The default stays exactly that, so the desktop gate's (c) `bulkSimAsync == 0` and (h) golden keep passing. The harness sets a `localStorage` key before navigation; `simRunner()` reads it once and constructs `BulkHttpSimRunner(this.sim.concurrency)` — the same construction 403 removed (C7). A fresh Chromium profile per harness launch means the key never leaks.

**Measurement harness.** `run-tab-cdp.mjs` gains `--bulk-http`, `--iterations N`, and two timings: `firstRowS` (Run click to the first `.upgrades-results table.upgrades-results-table tbody tr`) and `clickToDoneS` (click to the `Took` status). Server stderr is captured to a file by a small stage script (the gate script discards it, C12) and parsed with the existing `parse_bulk_stage_timings.py` for the finalist share.

### Q1 — cap: Candidate A (cap 40) wins

- Pre-registered win condition (from the brief): B wins only if there is a prior reason to expect the first-row / end-to-end ordering to flip between cap 20 and cap 40.
- Prior evidence (C19): screened vs loop was 264 s vs 13 s at cap 20 and 263 s vs 19 s at cap 40 — same direction, and the full pool (3419 s vs a projected 149 s) is also the same direction. Nothing on record shows an ordering flip with cap. Post-fix, both arms' cost grows with the candidate count (bulk per chunk, loop per candidate), and bulk's first row structurally waits for every chunk (C20), so a larger cap can only move the first-row ordering *against* bulk, never toward a flip in its favour. No flip reason exists, so A wins on cost.
- Additional reason A is the better single point: cap 40 is two chunks (25 + 15), which exercises the chunk loop; cap 20 is one chunk, and 403 recorded the 17-set chunk skipping the finalist stage entirely. Cap 40 also has the committed golden as the accuracy anchor.
- Candidate B dropped: no stated flip reason; roughly double the run cost.

### Q2 — fixed-not-bypassed: Candidate A (finalist-share assertion) wins, with a named alternative signal

- What the harness/readback exposes: nothing about stages — the readback has no `StageMetrics` (397 searched all three readbacks, zero matches), and `check_desktop_tab.py` sends server stderr to `DEVNULL`. What the **server stderr** exposes: `[Bulk Sim] - Stage: finalist - Started\n  Finalists: N\n  Iterations so far: I` and `... - Finished ... Iterations: J ... Duration: D s` per chunk (C12). The stage script captures stderr; `parse_bulk_stage_timings.py` already parses exactly these lines.
- Pre-registered check: across the three deciding bulk runs, (i) every `Finalists:` line reads `5`, never `25` or `15`; (ii) on every chunk where the stage ran, exit `Iterations` > entry `Iterations so far` (refinement happened) and `Duration` > 0; (iii) finalist share = Σ finalist `Duration` / Σ `elapsedS` over the three runs is **< 40 %** (well below the 60–73 % seen ungated); (iv) `go -C vendor/tbc-new-fork test ./sim/core/bulk/` passes the new unit tests that assert the refined finalists' metrics are the ones in the response.
- Alternative signal (required by the brief if the share is unobservable): the stage may legitimately skip a chunk when no adjacent pair is unresolved at 95 % (`stage.go:264`), and with 5 finalists that is more likely than with 25 (C25). If **no** chunk in any deciding run logs a finalist line, the share is recorded as 0 with the reason "skipped by the stage's own convergence test", and fixed-not-bypassed rests on (iv) plus the diff review: the fork commit adds no early return and no guard around the `runBulkSimFinalistStage` call. The measurement record must say which of the two signals carried the check.

### Q3 — decision rule (written before measuring)

Arms, all at cap 40, ret P5, packaged `wowsimtbc.exe` on `:3333`, fork tip built from the plan's commit, machine otherwise idle:

| Arm | Runner | Tab iterations | Repeats | Role |
| --- | --- | --- | --- | --- |
| P (probe) | bulk-http | 3000 (default) | 1 | measures the High stage's realised iteration count → `I_match` |
| B | bulk-http | `I_match` | 3 | deciding |
| L | loop (default) | `I_match` | 3 | deciding |
| S | loop (default) | 3000 | 3 | context only (what ships today); never decides |

- **Matched accuracy (method, pre-registered).** The Go High stage treats `highStageIterations` as a floor and raises it to its 0.05 % target-error count (C11), so a bulk run at the tab's 3000 realises far more. Following 346's M2/M1 method: `I_match` = the largest `Iterations:` in any `high` stage `Finished` summary of the probe run, rounded up to the next 500. Both deciding arms run with the tab's iterations picker set to `I_match`, which drives both the loop's per-candidate sims and `highStageIterations` (C10). Accuracy is then checked two ways: (a) every B run's realised `high` iterations per chunk lie within `[I_match, 1.25 × I_match]` — if a chunk exceeds that, set `I_match` to the largest realised value, re-run L ×3, and record the retry (one retry allowed; a second overshoot is a stop-and-report); (b) `python scripts/check_desktop_tab.py --compare <B_i.json> <L_j.json>` exits 0 (T1–T4, same binary and transport so T3 is asserted) for every one of the 9 (B_i, L_j) pairs. A failing pair is a finding that blocks the verdict — stop and report, do not loosen the tolerances.
- **Metrics per run:** `firstRowS` and `clickToDoneS` from the harness; `elapsedS` (the tab's own `Took`) recorded alongside.
- **Noise bar (pre-registered):** three repeats per deciding arm; verdict on medians; "beats" on a metric means the bulk median is **≤ 0.85 ×** the loop median **and** the arms' `[min, max]` ranges do not overlap. Basis: loop cap-40 wall clock repeated 19, 19, 18 s in prior runs (~5 % spread), while screened runs varied 173–264 s between identical runs (C18), so a 15 % margin is three times the loop's spread and the range rule guards against bulk's larger variance.
- **Verdict:** **KEEP** (406's ruling stands) if and only if bulk beats the loop on **both** `firstRowS` **and** `clickToDoneS` under the bar above, **and** the Q2 check holds, **and** the accuracy checks (a)(b) hold. Otherwise **DELETE** — bulk loses or ties within noise on either number, and 406's measured-clean delete (fork `5c2b1d7f9`, core `ca5c7040`) is the follow-up. This plan records the verdict; it does not perform the delete (Out of scope).
- Stated prior, not a rule: `screenCandidates` is one `await` before any row lands (C20), so bulk's first row cannot arrive before both chunks finish. That predicts a DELETE verdict; the run decides, not the prediction.
