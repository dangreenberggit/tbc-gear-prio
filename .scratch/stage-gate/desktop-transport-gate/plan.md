## Approach

**Four transport signals; the gate needs all of S1–S3 and the screen check.** The tab's `simRunner()` (`<tab>/upgrades_tab.tsx:1159-1169`) swallows any probe failure and returns the factory runner, so completion proves nothing (C1).

- **S1 — runner class**: `data-runner` attribute on the status element, written from a string literal chosen by `instanceof BulkHttpSimRunner` (not `constructor.name`, C5), removed at the start of every run (F4). Necessary, not sufficient: the fallback under-claims (`WasmSimRunner`), it never over-claims.
- **S2 — completed bulk responses**: count of `Network.responseReceived` with status 200 whose URL path ends `/bulkSimAsync`, summed over the page session and every auto-attached worker session (C25). Independent of anything the tab reports. Zero on the WASM page (the WASM worker's `bulkSimAsync` is a throwing stub, C3) and zero on the fallback (C27).
- **S3 — served worker body**: plain HTTP GET of `sim_worker.js`; the embedded server rewrites it to `net_worker.js` (C2). Independent of the browser.
- **S4 — fallback warnings**: count of page-console messages starting `[upgrades] screening fell back` (C30). Must be 0 on a clean screened run; distinguishes "screening ran" from "screening was attempted and every chunk failed to the loop". Emitted only after `rankUpgrades` returns, so the signal is meaningful only on a run that completed (G4).

**The screened path (F3).** On the HTTP transport, `rankUpgrades` prices candidates through `runBulkScreen` (C7) and publishes the screened delta for every row except the top 8 above the cutoff, which `replicateTopItems` re-prices through `deps.sim.run` at seeds 11–55, overwriting `deltaDps` and recomputing `belowCutoff` (C29). The baseline scalar comes from the loop route on both transports, so it cannot detect a wrong screened number. The assertion that can: run the same capped candidate set twice on the **same binary and transport** — once screened (normal) and once through the tab's own fallback runner, which on 3333 is the page's HTTP worker pool with no `runBulkScreen` (C27) — and compare rows by `(item, slot)`:

- **T1** — the row key sets are identical. Fails on a dropped or truncated candidate (chunking, `topResults`). **Limit:** a screening error that only changes *which* rows enter the top 8 leaves the key set intact (same items, same slots); that case is covered by T2 on the rows it pushes out and by T4.
- **T2** — for every row **outside the top 8 of both runs** (rows 9..N), `|Δ_screened − Δ_loop| ≤ K`, `K = 12.0 DPS`. The top-8 rows cannot fail T2: both runs re-priced them identically through the loop route (C29), so T2 says nothing about screening there. Derivation of K: the ret cutoff is the committed 2×SE bar `3.4 = 2 × 1.678` (`cutoff.ts:37`, C28); if the two routes' RNG streams differ (the ledger's 65.3 DPS probe gap says they do in practice, C28), a paired delta's route-to-route difference has SD ≈ √2 × 1.678 ≈ 2.4 DPS, and 5 SD is 12. A mapping bug (item X priced as item Y) moves a row by the spread of deltas between items — tens of DPS on this pool (top row +57.7, most rows negative, C19) — and fails T2; seed noise passes it with a per-row false-fail probability ≈ 6 × 10⁻⁷.
- **T3** — for rows that are top-8 above cutoff in **both** runs, `|Δ_screened − Δ_loop| ≤ 0.3 DPS` (the shared-route agreement rank.ts records, C12): these rows come from identical `/raidSimAsync` requests to the same server in both runs (C29), so they must agree to display precision. **T3 is the only check covering rows 1..8, and it tests server determinism, not screening.** A failure here means the server is not deterministic at a seed, which invalidates T2's model and is recorded as a finding.
- **T4** — `|median(Δ_screened − Δ_loop)| ≤ 3.4` over all rows (the committed cutoff bar). `bulk_screen_driver.ts:113-115` keeps only the first chunk's baseline for the whole batch, so a uniform offset applied to every screened row is a reachable bug class; an offset under K passes T2 on every row, and the median is the instrument that catches it (the 65.3 DPS hazard rank.ts documents is the large case).
- **Recorded, not asserted**: the max per-row difference beside K, the above-cutoff set symmetric difference, and both baseline scalars.

**Cost.** One extra capped run per gate invocation. At the gate's default `--candidates 40` the loop run is ≈ 40 sims + 8 × 5 replication + 5 baselines ≈ 85 sims; the WASM page did 646 sims in 1896 s ≈ 2.9 s/sim (C32), so the twin is ≤ ~4.2 min if the native server is no slower than WASM — measured in step 7 and recorded. The full-pool version of the same comparison across transports (3333 screened vs WASM page loop) costs nothing extra: step 5 needs both full runs anyway for Q2, and T1, T2 and T4 are applied to them as stage evidence (T3 there is cross-compilation, recorded only). `--no-screen-check` skips the twin for a quick transport-only run; the default is on.

**Negatives.** N1: `--usefs=true --wasm=true` makes the same binary serve real WASM from `./dist` (C2) — S1, S2, S3 all fail. N2: `--force-fallback` makes the **next single** `new window.Worker` throw synchronously once the page is loaded and before Run; `new WorkerPool(1)` throws inside the `try` and the tab returns `this.sim` (C26) — the run **completes** over HTTP with S1 = `WasmSimRunner`, S2 = 0, S3 passing. The throw is one-shot so a mid-run pool respawn (`enable()` → `setupWorker()`, G1) constructs normally. N2 is the brief's false-pass scenario and the gate refuses it on two signals the tab does not control. N2's run is also the T1–T4 partner.

**Reshaped tests, restated.** The parent's per-row SE comparison is unshaped because SE is not in the DOM (C11) and because the two transports price rows by different procedures (C7); revision 1's replacement measured only the shared route. Revision 2 keeps the parent's intent — per-row agreement — and gets it from the observable that isolates the screening procedure (same engine, same transport, screened vs loop), with tolerances from committed constants. Q1 (bundle integrity) stays a byte comparison. Gate assertion (e) compares against the page's own declared pool and a pinned committed count (F8).

**Strongest rejected alternative.** Blocking `/bulkSimAsync` with CDP `Fetch` on the worker sessions to force the engine's chunk-failure fallback (`bulk_screen_driver.ts:117-133`, `rank.ts:935-940`). It gives the same unscreened run but needs a second intercept mechanism and produces S4 warnings by design, muddying the signal. The `window.Worker` throw exercises the exact `catch` the brief names and reuses one switch for N2 and the twin.

**Serial, one clone.** No fan-out. **`pnpm verify` is red in exactly two windows, by design:** (i) in step 8 between the fork commit and the lock edit (fork HEAD ≠ lock `commit`), and (ii) in step 9 while the clone is on `5e9013b78` (HEAD ≠ lock; universe copies differ). Uncommitted tip edits in steps 3–7 leave HEAD = lock, and `fork-lint:check` lints the working tree, so verify is expected green there once the harness lints clean; no step before 8 runs `verify` as an acceptance.
