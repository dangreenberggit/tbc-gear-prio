# Plan — two-hander-clears-offhand (revision 1)

## Goal

When `rankUpgrades` prices a two-handed candidate into `mainhand` for a character wearing a one-hander plus an off-hand item, the composed sim request has the off-hand slot empty, the row's stat delta debits the removed off-hand item, and the row carries a new `removedItems` field that the CLI, the HTML report and the fork tab render, so a reader cannot mistake the two-item change for a one-item swap. Both engine copies (`packages/core/src/rank.ts` and the fork's `upgrades/engine/rank.ts`) carry the change; the fork commit is pinned in `data/wowsims-fork.lock.json` and pushed to the personal fork. Every spec with no off-hand item worn, and every non-two-handed candidate, produces byte-identical ranking output before and after. A unit test at `rankUpgrades` fails before the fix and passes after.

## Approach

### Q1 — where the clear belongs

Winning condition, stated before measuring: the site must be reached by **every** path that composes candidate equipment (single-candidate loop, set-value package loop, and the fork's bulk screening pass), must run **before** the candidate's gem fill so the fill does not count gems on the item being removed, and must have a return channel for the disclosure. Ties break toward the smallest number of call sites changed.

| Candidate | Reached by all composition paths? | Runs before gem fill? | Return channel for disclosure? | Call sites changed |
| --- | --- | --- | --- | --- |
| (a) slot loop beside the `offhand` guard (`runCandidate` in core; `attemptEligibility` in the fork) | No — the fork's `screenCandidates` and the package loop call `candidateSwapWithRepairs` directly, so they would still compose 2H+OH sets and the screen would price a different set than the loop (C7) | n/a | Would need plumbing | 2 (loop) + 1 (screen) + 1 (package) |
| (b) `swapItemAt` | Yes — one caller, `candidateSwapWithRepairs` (C5) | Its own fill runs off `fillOptsForSwap(equipment, …)` computed from the input array, so the clear would have to be spliced before that call inside the same function | None — returns `SimItemSpec[]`, so the disclosure would need a second return shape anyway | 1 |
| (c) `candidateSwapWithRepairs`, before its `swapItemAt` call | Yes — it is the single composition entry point for all three paths plus `equipmentForCandidateSwap` (C5, C6) | Yes — clear the input array first, then pass the cleared array to `swapItemAt`, so `fillOptsForSwap` never sees the off-hand's gems (C8) | Yes — it already returns `{ equipment, swaps }`, the disclosure channel ticket 107 built | 1 function + 2 consumers of the new return field |

**Chosen: (c).** The "widest blast radius" of `swapItemAt`/`candidateSwapWithRepairs` is the point, not the cost: every path that composes a candidate set must compose a legal one, and the condition is narrow enough (`slotIndex === mainhand`, candidate `handType === HandTypeTwoHand`, off-hand `id` truthy) that no other path can trip it. Placing the clear at the loop guard (a) is the strongest alternative because it sits beside the existing guard comment, and it loses because the fork's screening pass and the package loop would keep composing illegal sets — the fork's own PROVENANCE row says the two routes share `attemptEligibility` precisely so they cannot drift about which attempts exist, and (a) would reintroduce a drift about what those attempts contain.

**Ordering is load-bearing (C8).** `candidateSwapWithRepairs` calls `swapItemAt(equipment, …)` as its first statement today, and `swapItemAt` computes `fillOptsForSwap(equipment, slotIndex, gemCtx.spec)` from that same input array. The clear must therefore run **before** the `swapItemAt` call and `swapItemAt` must receive the **cleared** array. If the clear ran after `swapItemAt`, a unique gem on the removed off-hand item would still block the two-hander's socket and the meta count would still include it — wrong output that no test on this path would catch, because no test asserts gem internals here. Step 3 carries this as an explicit acceptance criterion.

Concretely, in both copies:

- Add a helper next to `swapItemAt` (name it `clearOffHandForTwoHander`) taking `(equipment, slotIndex, itemId)` and returning `{ equipment: readonly SimItemSpec[]; removed: readonly { slotIndex: number; itemId: number }[] }`. It returns the input unchanged with `removed: []` unless `slotIndex === SIM_ORDER.indexOf("mainhand")`, `getItem(itemId)?.handType === HandType.HandTypeTwoHand`, and `equipment[SIM_ORDER.indexOf("offhand")]?.id` is truthy; then it copies the array with the off-hand index set to `{ gems: [] }` (the bare-slot shape `equipmentFromLoggedGear` uses, C9) and `removed` naming that slot and item id.
- `candidateSwapWithRepairs` calls it **first**, passes the cleared array to `swapItemAt`, and returns `{ equipment, swaps, removed }`.
- The comment on the helper says why the clear is honest here and cites ticket 350 and the guard's scope paragraph. It must not contain the word "override".

### Q2 — gem repair after the clear

Candidates that differ in kind: (i) correct-and-expected — the emptied slot is indistinguishable from any bare slot the baseline already carries; (ii) a second defect — some gem stage reads the cleared slot and misbehaves (throws, invents gems, or double-counts). Winning condition, stated before measuring: (i) wins if every gem stage on the candidate path already handles a `{ gems: [] }` / `itemId: 0` entry by skipping it, and the baseline path already runs those stages over such entries today.

Measurement (C9, C10, C11, C12): `equipmentFromLoggedGear` writes `{ gems: [] }` for any slot the log leaves empty; `socketedItemsFromLoggedGear` maps it to `itemId: 0`; `repairMeta` returns early when `getItem(head.itemId)` is undefined and `bestRepairMove` does `if (!item) continue` for every slot with no item; `allGemIds` reads only `gems`, which is empty; `applyRepairedGems` returns the spec unchanged for `!spec.id`; `sumStat` skips `!spec.id`; `toProtoItem` emits `{}`. The baseline already runs `repairAndMinimize` over `itemId: 0` entries for every empty slot of every character (the ret fixture's off hand is empty because slamaltman wears the two-hander 28430 Lionheart Executioner, C13). So (i) holds: **the gem output for those candidates changes, and the change is correct** — gems on the removed off-hand item no longer count toward the candidate's meta condition and no longer block a unique gem in the two-hander's sockets, because the clear runs before `swapItemAt`'s fill (C8, load-bearing). This is the same consequence the brief already names ("one fewer socketed item"), not a second defect. No new test asserts on gem internals; T1 and T4 below run the full path through `rankUpgrades` and would surface a throw.

### Q3 — disclosing the two-item change

Candidates that differ in kind: (a) a new optional structured field on the row, following the `gemSubstitutions` precedent (absent, never `[]`); (b) a free-text `setBonusNote`-style string; (c) the run-level `Ranking.substitutions` list; (d) fold the removed item into `gemSubstitutions`. Winning condition: the field must be per-row (the fact is about one row), structured (a renderer needs the item id to name and link it), and rendered by every reader surface that shows rows — CLI text, HTML report, fork tab.

**Chosen: (a).** `RankedItem.removedItems?: Array<{ itemId: number; slot: SimSlotName }>` in both copies, declared in the **row** type (`RankedItem`), not the package type (`SetBonusValue`), with the same absent-never-empty convention as `gemSubstitutions`. Each copy declares `gemSubstitutions` twice — once on the row type and once on the package type (C25) — so the insertion anchor is the row-only field `emptyMetaSocket?: boolean;`, which occurs exactly once per copy: the new field goes immediately **before** it. (b) loses structure; (c) is run-level and `gemSubstitutions`'s own comment records that per-row facts do not go there; (d) lies about the kind of change. The row text, in each surface:

- One pure formatter in `packages/core/src/rank-report-rules.ts`, `formatRemovedItemsLines(item: Pick<RankedItem, "removedItems">): string[]`, returning `[]` when the field is absent and otherwise one string per entry: `removes worn: <getItem(itemId)?.name ?? String(itemId)> (<slot>)`. `rank-report-rules.ts` already imports `getItem` and is already imported by both `cli.ts` and `rank-report.ts` (C26); `formatSetPotentialLine` is the precedent — a row-note formatter that lives there and is unit-tested by hand-built rows in `cli-shortlist.test.ts` rather than by capturing stdout (C27).
- CLI (`packages/core/src/cli.ts`, inside the `printRow` closure beside the `item.setBonusNote` branch): `for (const line of formatRemovedItemsLines(item)) console.log(...)` with the file's existing indent.
- HTML report (`packages/core/src/rank-report.ts`, beside the `gem-subs` div): one `<div class="removed-items">${esc(line)} — a two-hander leaves no off hand</div>` per formatter line.
- Fork tab (`upgrades_tab.tsx` `resultRow`, a `<small className="upgrades-removed-items">` line under the delta, like `setBonusLine`): i18n key `upgrades_tab.results.removes_worn` = `"removes worn {{name}} ({{slot}})"`. The name comes from `Database.getSync().getItemById(itemId)?.name`, the same lookup `itemCell` uses.

The tab string needs one key in `assets/locales/en/translation.json` and, in `schemas/translation.schema.json`, both a `"removes_worn": { "type": "string" }` property under `upgrades_tab.results.properties` **and** a `"removes_worn"` entry in that object's `required` array. The `required` edit is mandatory: the object lists all 18 existing keys as required and sets `additionalProperties: false` (C16), so a missing property makes `test-locales.mjs` fail, while a missing `required` entry passes silently (AJV checks only that required keys are present) and leaves a hole in the gate. Only `en/` exists under `assets/locales/`, so there is no other locale to break. Both files are upstream files but the tab's established footprint (44 and 22 of our branch's commits); the orchestrator's Q3 ruling (decision log, 2026-09-10) allows them, additive only. If that ruling is withdrawn, the executor **stops and reports** at step 6 rather than hard-coding an English string in the tab.

### Q4 — proving the blast radius

Winning condition: a measurement at the module interface showing that for a dual-wield spec over its whole universe, every candidate request differs from baseline in exactly one item index unless the candidate is a two-hander, and that every existing pinned-number test and the cross-engine parity test stay green.

- T3/T4 (new, green before and after): with `vendor/wowsims/warrior_p2_fury.gear.json` worn (MH Dragonstrike 28439, OH Talon of Azshara 30082 — C14) and the full `warrior-p2` universe as pool, every captured request's set of indices whose item id differs from the baseline has size 1, except requests whose index-14 item has `handType === HandTypeTwoHand`, where it is exactly `{14, 15}` with `items[15]` equal to `{}`. Before the fix the exception branch fails (size 1 with the off hand still worn); after, both branches pass. A second run with `warrior_p2_arms.gear.json` (2H worn, off hand empty — C14) asserts no row carries `removedItems` and every request differs in exactly one index — that is the guard's own case, unchanged. Rogue is covered by `rogue-p2` carrying zero two-handers (C15): the clear condition is unreachable, and the existing rogue archetype test stays green.
- Existing suite: `rank.test.ts`, `synthetic-fixtures.test.ts`, `archetype-specs.test.ts` pin ret/feral/shadow/rogue/warrior/hunter outputs; `wowsims-fork-parity.test.ts` (E-W3) runs both engines on the ret fixture and `toEqual`s composed requests and projects rows onto a fixed field list (C17). All green is the before/after proof for unaffected specs. E-W3 stays green between steps 3 and 5 (core changed, fork not yet) because its row comparison is a field projection that excludes optional disclosure fields, and slamaltman's empty off hand means the clear cannot fire on either engine (C13, C17).
