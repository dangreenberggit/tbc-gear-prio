# Plan — skeleton-scope-and-local-dev-fixture (revision 1)

## Goal

When this plan is done, the repo says in writing — in a place every exploring agent reads first — that the raid-sim skeleton (`data/presets/<spec>/p2.raid-sim-skeleton.json`) is a CLI-harness input and that the wowsims Upgrades tab never reads one, so "2 of 11 skeletons exist" is a CLI test-coverage limitation and not a product gap. Concretely: ADR-0031 records the decision with its evidence; `CONTEXT.md` carries a glossary entry `raid-sim skeleton` pointing at it; ticket 365 is rewritten as a CLI-only test-coverage gap with its stale ticket-362 sentence removed; ticket 350 is unblocked (`Blocked by: none`) and records option 2 (clear the off hand, disclose the loss) as the mirror case of the existing off-hand guard in `packages/core/src/rank.ts`, not as an override of it; that guard's comment in `packages/core/src/rank.ts` gains a scope statement (comment-only, no logic change, fork copy untouched); the parked plan at `.scratch/stage-gate/ticket-365-dual-wield-fixture/plan.md` carries a superseded header; ticket 367 exists as `Status: open`, recording that a generated local-dev skeleton set has zero consumers today and naming the condition that reopens the work; `NEXT` reads `368`; no logic changes in any code file; `pnpm -C <repo> verify` is green on the tip when run from Bash.

## Approach

**Chosen: documentation-plus-one-comment stage that answers Q1–Q4 from measurements already taken, builds no generator, and records the decision as an ADR plus a glossary pointer.**

Q2 was measured first, as the brief demanded, and it forces Q1. Three independent gates sit between a committed skeleton and a CLI ranking, and a skeleton clears none (C3, C4, C5):

1. The `pnpm rank` front door — `parseArgs` in `packages/core/src/cli.ts` — rejects any `--spec` except `ret`/`feral` (`unknown spec: enh (known: ret, feral)`, exit 2) before any file is loaded. This gates that one entry point only: `rankUpgrades` is also called directly by `packages/core/test/archetype-specs.test.ts` with shadow/rogue/warrior/hunter, but those callers supply their own in-line request and read no preset file (C3, C7).
2. `pnpm rank` has no live path (`live WCL path is not wired yet; pass --offline`), so every run is offline (C4).
3. Offline, `offlineGearRecordings` in `packages/core/src/cli-wiring.ts` returns `undefined` for any character outside `RECORDED_CHARACTERS` (one ret, two feral); the run then ends `no-qualifying-fight`, exit 1 — measured on ret, which *has* a skeleton (C5).

The only reader of a committed skeleton is `loadOfflineInputs` in `cli-wiring.ts`, which builds the path by template (`data/presets/${spec}/p2.raid-sim-skeleton.json`), so a literal-path grep cannot show absence of readers. The correct measurement is the caller census: `loadOfflineInputs` has exactly three call sites — `packages/core/src/cli.ts`, `apps/web/server/wiring.ts`, `apps/web/test/recordings.ts` — and each is independently gated to ret/feral (C6). The all-spec tests build a tab-shaped skeleton in-line (C7), and the tab calls upstream's `sim.makeRaidSimRequest(false)` (C8). Nine generated skeletons would therefore ship files nobody opens. "Build none" wins Q1 on measurement.

**Strongest rejected alternative: build the subset generator (balance, shadow, ele, enh — the four specs with one `p2.gear.json` and one `default.apl.json`).** It looked cheap because the structure generalizes (copy ret's encounter block, blank 17 slots, gate the APL through `scripts/apl_schema.py`). It loses because the generated files would still have zero readers (C6) and because ADR-0022 forbids reusing ret's buff blocks, so each spec needs its own extraction — `scripts/extract_sim_defaults.mjs` has one `SPECS` entry and `vendor/wowsims/` vendors one `sim.ts` (C10). That is four new `TRACKED` entries plus extractor plumbing to produce artifacts no consumer reads. The reason is recorded in ticket 367 so the next agent does not re-price it.

**Why 367 is `open`, not `wontfix`.** The plan itself names the condition that makes a skeleton useful: extend `parseArgs` past ret/feral and route a preset gear set through `syntheticOfflineRecordings` as a synthetic character. A skeleton would be the input to that route. That is a deferral pending a consumer, and `wontfix` is the one status that tells future agents never to look again — the failure mode this stage exists to stop. So 367 is filed `open` with the "no consumer today" finding and the reopening condition in its body (C15).

**Second rejected alternative for Q4: a comment at the `cli-wiring.ts` load site plus the tab adapter.** Loses because the tab adapter lives in the gitignored fork checkout — a comment there is a ported-engine-adjacent edit on an unpushed branch (211 commits on no remote, C13) — and a comment in `cli-wiring.ts` is read only by someone already inside the CLI, which is not where the confusion starts. Tickets alone lose because tickets close and stop being read. An ADR alone loses because `docs/agents/domain.md` tells engineering skills to read `CONTEXT.md` first and ADRs only "that touch the area" — an agent who does not know the area is the one who re-derives the confusion. Hence: ADR-0031 holds the record; `CONTEXT.md` holds the term and the pointer.

**Ticket 350 and the off-hand guard: two cases, not one position overridden.** The guard comment above `if (slotName === "offhand" && !mainHandIsOneHanded) continue;` covers the case where a two-hander is already **worn** and a one-hander is offered as an **off-hand candidate**: equipping it gives 2H + 1H, which the game cannot equip, so the guard skips it; and the comment rejects the alternative remedy (displace the worn two-hander) because that row would price a one-hander while silently costing a two-hander. Ticket 350 is the mirror case: a one-hander plus an off-hand item is worn and a **two-hander is the candidate** for the main hand. The guard never fires there, because it tests only candidates aimed at the off hand. The remedies differ because the outcomes differ: clearing the worn two-hander (comment's case) leaves a strictly worse setup and a dishonest row; clearing the worn off-hand item (350's case) leaves a legal, ordinary two-hander build and an honest one-for-one swap. The owner ruled on 2026-09-10 that the guard stands as written and that there is no conflict to resolve. So option 2 is recorded as the handling of the mirror case, and the guard comment gains a scope statement (Step 6) so the next reader does not need the long read to see which case it covers. The fork's ported copy carries the same comment but is left alone: known-traps § "Before editing a ported engine file" arms the five-step cycle for comment-only edits too (C20), and the core comment is not an input to that gate (C21).

**Gate C decision.** `pnpm verify` is not a precondition to report back; it runs today from **Bash**, where the fnm multishell resolves Node 22.17.1 and `pnpm --version` prints 11.24.0 (C1). PowerShell still resolves `C:\Program Files\nodejs\node.exe` 20.18.1 and pnpm dies on `node:sqlite` (C2). Verified green on the base SHA from Bash (C1). The executor runs verify from Bash only, confirms `node --version` prints v22.x first, and falls back to the PATH pin in `docs/agents/known-traps.md` § "Before running node / pnpm / test commands" if a shell loses fnm. No Node install, no ticket 268 work.
