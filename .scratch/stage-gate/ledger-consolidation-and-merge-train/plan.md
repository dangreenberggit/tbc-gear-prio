Revision of the plan reviewed in `plan-review.md`. Every finding F1–F12 is addressed in a step or a claim row; the `## Review findings` section at the end maps each one. The C6 restructuring (merge order is free with respect to the fork pin) is unchanged.

## Goal

When this plan is done: `docs/fork-upstream-touchpoints.md` is the only tracked document answering ticket 369, containing session B's four items (the `sim_header.tsx` conflict history, the `test-layout.mjs` non-divergence row, the resolved `ui/core/sim.ts` row, and a merge-conflict section with B's "What changed / Why / Risk" columns) with the stale "throws at runtime" wording corrected; `docs/fork-upstream-divergence.md` is deleted in the same commit; every inbound link resolves to the surviving file. The 13-vs-15 reconciliation is re-derived with recorded commands and stored in the stage directory, and the document records why session B's "undercount" claim was wrong. The two already-merged branches are deleted. Tickets on `feat/spec-registry` are renumbered 376–378 and on `fix/sim-header-null-assertion` 379–380, with `NEXT` on `docs/fork-upstream-touchpoints` raised to 381 so the reservation lands on `dev` with the first merge; ticket 372 (renumbered 377) is closed as an inverted diagnosis. Each of the three surviving branches has `dev` merged in, `pnpm verify` green, `python scripts/check_merge_ready.py` printing `merge-ready: ok`, and `pnpm merge-to-dev --check-only` rc 0 printing `check-only: ok (not merging)`, with the fork clone positioned at that branch's pin. A written, measured merge order (`merge-order.md`) states the pin and clone state at each step and carries the old→new ticket-number map as the decoder ring for commit bodies that keep the old numbers. No `pnpm merge-to-dev` has been run by the executor; the clone sits at `dev`'s pin at handoff.

## Approach

**Chosen.** Do the fold on the existing `docs/fork-upstream-touchpoints` branch after merging `dev` into it (so both documents are in one tree), then prepare the other two branches in place: merge `dev` into each, resolve the conflicts the merge dry-run predicts (working tree **and** index — `git add` after every resolution), renumber tickets, re-resolve every `defer` row path, and prove each branch with `check_merge_ready.py` and `pnpm merge-to-dev --check-only`. The owner merges in the order consolidation → `feat/spec-registry` → `fix/sim-header-null-assertion`. Work is split into **Phase A** (executable now, no owner action) and **Phase B** (steps that can only run after a named owner merge). The executor stops after Phase A and hands off if the owner does not merge during the stage.

**Rejected alternative: one integration branch.** Merge all three branches into a new `feat/merge-train` branch, resolve every conflict once, land once, move the clone once. It loses because `pnpm merge-to-dev` looks up the review file by branch name (`scripts/check_merge_ready.py:151`, `review_path`), so the integration branch would need a fresh three-axis review while the three existing review files would go unused. It also merges two reviewed code branches under one commit, which the reviews did not examine together. Pin safety, which was the reason to consider it, turns out not to need it (Q1).

**Rejected alternative: fold into session B's document instead.** Session B's own document recommends folding into session A's, session A's carries the owner's constraint quote and the per-file avoidability analysis (13 sections), and the brief fixes the direction. Not re-litigated.

**Rejected alternative: rewrite commit messages to match the renumber.** The commit bodies on both branches name 371/372/373 (C21a). Rewriting them means rebasing reviewed ranges, which invalidates both review files. Instead the old→new map is recorded in `merge-order.md` and in each renumbered ticket, and the plan states plainly that commit-message ticket numbers are knowingly left stale (F5).

### Ticket-number allocation (F7, F8)

Fixed by this plan, not chosen at run time:

| Branch | Tickets it carries after renumber | `NEXT` it commits | Merge position |
| --- | --- | --- | --- |
| `feat/spec-registry` | 376, 377, 378 (were 371, 372, 373) | 379 | second |
| `fix/sim-header-null-assertion` | 379, 380 (were 371, 373) | 381 | third |
| `docs/fork-upstream-touchpoints` | none, or 381+ if the A5 review defers findings | 381 before any filing; 381 + k after k filings | first |

Mechanisms, in order of strength:

1. Ranges are disjoint by construction and written here; no step decides a number by looking at another branch. Step A5a raises `NEXT` on the touchpoints branch to 381 **before** its review runs, so any ticket it files is ≥ 381, and Step A8 sets 381 unconditionally (no "or 382").
2. `NEXT` is edited on every branch, so any two of them merging into `dev` conflict on `NEXT` (C7, C8, and touchpoints once A5a lands). The resolution rule is one line and deterministic: **`NEXT` = the larger of the two sides.** It is written in `merge-order.md` and applied in B1/B2.
3. The touchpoints branch merges first and carries `NEXT`=381+ plus a `map.md` line stating "376–380 reserved on `feat/spec-registry` and `fix/sim-header-null-assertion`, see `merge-order.md`". After that merge a `dev`-based session sees the reservation in the two places it reads to allocate (`NEXT`) and to orient (`map.md`).

Residual risk, stated plainly: **until the owner merges the first branch, `dev`'s `NEXT` stays 376 and nothing on `dev` records the reservation.** A session filing a ticket from `dev` in that window would take 376. The collision would not be silent — that session also edits `NEXT`, so its merge and `feat/spec-registry`'s conflict on `NEXT` and the loser renumbers — but it costs a renumber. The executor's handoff message to the orchestrator names this window explicitly (Step A9), and the orchestrator relays it to the owner; the plan cannot write to `dev` to close it.
