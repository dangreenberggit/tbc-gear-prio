# Plan — tickets-306-308 (revision 2)

## Goal

Two tickets close on `feat/upgrades-dedup-wowsims`. For 306: the fork's `fmt` gate becomes a usable pass/fail signal by adding a scoped gate covering only the ten files this project owns — those files are formatted once, the scoped check exits 0, and a new `fmt` row in `fork-gates.md` records the scope and the reasons for each exclusion. For 308: second-copy placement is recorded as **deliberately out of scope**, with the reasoning written as a comment at the guard in both engine copies and at the `rowsTable` owned-row filter, so no future reader re-derives the question; a follow-up design ticket captures what implementing it would actually require. Both tickets are updated with the decision and closed. No ranking behavior changes.

## Approach

**Q1 (306).** Chosen: **add a scoped `fmt` gate over the files we own**, format exactly those files once, and document the exclusions.

- Corrected inputs (the brief's base figure was wrong — measured with oxfmt run against a worktree *path*, which silently loses `.oxfmtrc.json` and scans 674 files): run from **inside** the worktree, tip = 194 failing, base `cbf6b75a889e` = 85 failing, difference = 109 (C3). Of the 109: 65 are `upgrades/data/**` generated artifacts (`.ep-weights.json`, `.universe.json`, `upgrades/data/PROVENANCE.md`), **34** are `upgrades/engine/**`, and the genuinely-ours remainder is **10 files** (C16), enumerated in the Paths manifest. The tenth, `upgrades/engine_provenance.ts`, sits one directory *above* `upgrades/engine/` so neither exclusion catches it; it is hand-maintained and ungated, so it is ours (round-2 review G1).
- Pre-stated win condition (restated for the corrected numbers, before A1 re-measures): the owned set, after excluding `engine/**` and `upgrades/data/**`, is small (~10 files), consists only of files whose fork history shows our commits, and formats with the fork `tsc` gate still green. If A1's recomputation deviates from the enumerated 10-file list, the executor stops and reports rather than formatting a different set.
- `sim_header.tsx` sits outside the upgrades tree but **is ours to format**: its upstream-base version passes the check and its redness at tip can only come from edits made on this branch (the tab registration). A1 confirms this with `git -C vendor/tbc-new-fork log --oneline cbf6b75a889e..HEAD -- ui/core/components/sim_header.tsx` showing our commits; if that log is empty the file is dropped from the set and the anomaly reported.
- Exclusions, each with its reason written into the gate doc: `upgrades/engine/**` — byte-gated by `scripts/check_engine_port_drift.py` under `pnpm verify` against `engine/PROVENANCE.md`; reformatting stales the hashes (C9). `upgrades/data/**` — committed **generated** artifacts plus their own `PROVENANCE.md`; hand-reformatting generated bytes violates the durable-claims rule and no regenerator would reproduce the result (C16). Upstream's 85 — inherited redness on a commit we never touched; not our fight (brief constraint 4).
- Strongest rejected alternative: **drop `fmt` from the gate set and document three gates.** It loses because it forfeits the only formatting signal over our own code — `pnpm verify` never touches the fork (C10), so a future regression in `upgrades_tab.tsx` or the adapters would be caught by nothing. The scoped gate costs one 10-file mechanical commit and keeps that signal. A regression in upstream's or the generated files stays invisible under both candidates, so that limb does not separate them.
- Dropped: **reformat all 194** — ruled out by brief constraint 4 and now also by F3's composition (it would hand-rewrite 65 generated files). **Fix the config** — no evidence it is wrong: the config is upstream's own (`7e8fcb3d2`), oxfmt is pinned `^0.62.0` with 0.62.0 installed (C2), and upstream's own pristine tree fails it when the config is correctly resolved (C3): the tree is unformatted, the config is not misconfigured.

**Q2 (308).** Chosen: **record second-copy placement as deliberately out of scope**, with the reasoning written at the guard in both copies and at the owned-row filter, plus a follow-up design ticket.

- Pre-stated win condition, before the measurements below were taken: **implement** would win if teaching the ranker item uniqueness were a bounded guard-level change — data present, a row able to carry the "wear a second one" meaning without redesign, and the committed fixtures able to measure red/green honestly. **Record out of scope** wins if any of those limbs fails structurally rather than by missing effort.
- Three measurements each refute a limb, so out-of-scope wins:
  1. **The guard is not the only suppressor.** `rankUpgrades` emits **one row per item**, not per placement: `let best: BestSwap | null = null` before the slot loop, `if (!best || deltaDps > best.deltaDps)` inside it, one `RankedItem` per pool entry (`packages/core/src/rank.ts:903-1075` — C13). Relaxing the guard makes `finger2` *compete* with the owned ring's ~0-delta identity swap and **overwrite** it: the row silently changes meaning from "you already wear this" to "wear a second one" with nothing saying so — a silent wrong answer, the project's named worst case. A correct implementation needs a per-placement row concept: engine output shape, view, and UI all change.
  2. **The fixtures cannot measure it honestly.** `RecordedSimRunner.run` keys on a sha256 of the whole request and throws `no recording for sim key ${key}` on a miss (`packages/core/src/seams/sim-runner.ts:59-75` — C14). A duplicate-ring request is necessarily a miss, so no offline probe can distinguish "the sim rejects duplicate equip" from "no fixture exists", and a red test would be red for the wrong reason; going green would require fabricating a recording whose DPS is chosen by hand, deciding the test's outcome in advance.
  3. **The UI has no worn-slot signal.** A `ViewRow`'s `owned` comes from `equippedIds.has(entry.itemId)` (`rank.ts:897` — C15): it records *that* an item is worn, never *where*, so the owned-filter adjustment an implementation needs has no left-hand side without additional plumbing.
- Dropped candidate: **implement**, for the three structural reasons above — it is a per-placement redesign spanning engine output, recorded fixtures (new live recordings, not fabrications), and view/UI plumbing, far beyond this pipeline's scope. What survives of it: the data side is genuinely ready — `unique` is fully populated (1,409 true / 6,844 false over 8,253 items; 163 of 735 rings+trinkets non-unique — C4), surfaced on both engine item entries (C6), and currently dead data (C5). That readiness, plus the redesign shape, goes into the follow-up ticket so the work is deferred with its map, not lost.
- The cost comparison now genuinely favors this path: the comment edits pay only the ported-file cycle (which any touch of the fork engine pays), while implement additionally pays the F1 redesign, live fixture recording, and view plumbing.
- Ticket 308's third acceptance box ("revisit the `rowsTable` owned drop in the same change") is satisfied in its intent: the drop at `upgrades_tab.tsx:1439` (C11) stays **unchanged** because its safety argument — an owned item is only ever re-simmed into its own slot, delta ~0 — remains true while the guard stands; the revisit lands as an extension of the existing comment block (lines 1431-1438) naming ticket 308 and the guard coupling, so whoever implements per-placement rows finds the filter by reference, not folklore.

**Sequencing: Track B (308) first, then Track A (306), strictly serial, one executor, no fan-out.** The tracks share `vendor/tbc-new-fork/ui/core/components/individual_sim_ui/upgrades_tab.tsx` — B extends a comment in it, A formats it. Semantic-then-mechanical ordering keeps B's diff reviewable. B's new comment lines are written already oxfmt-clean so A2 does not rewrite them (F12). Each track ends in its own fork commit + re-pin; they must not interleave.
