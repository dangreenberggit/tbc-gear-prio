# Plan — upgrades-tab-ui-rebuild (revision 3, post-re-review)

## Goal

The Upgrades tab's run configuration lives in a sticky settings card in a right panel, copied from the Bulk tab's structure: count readout, primary Run action, then the config controls (Iterations, Candidates, BiS-prune, Phase) as real picker rows that wrap normally — and because the card is outside the sub-tab panes, Run stays visible on every sub-tab. The post-run view controls (Set potential, BiS only, Content) sit in the left panel above the sub-tab area, so they are visible and effective on every pane, with short control-name labels and the anti-jitter height reservation preserved. Rows with set context show how much of their figure is set bonus (ticket 313). A ThatsMyBis export box lives with the results and exports the sorted shortlist in displayed order (ticket 314). A dropped candidate shows only the first line of its error, with the full text in the console (ticket 311, presentation half). The inline status line is unchanged. All fork gates stay green.

## Approach

Copy the Bulk tab's two-pane settings-card structure, as the owner decided (ticket 312 "Owner's direction — decided"). The adversarial review confirmed the direction is sound (C1/C2/C3/C4/C21/C24 all hold); this revision fixes the map, not the destination.

**The corrected DOM model (review F1).** The tab's left panel (`.upgrades-tab-left tab-panel-left`, `upgrades_tab.tsx:389`) holds `.upgrades-tab-tabs` — a nav plus `tabContentRef`, whose panes are: the shopping-list pane (`shoppingListRef`, assigned to `this.shoppingListElem` at `:419`) and, appended later as **siblings**, the per-slot panes (`:1194`). The entire toolbar — run controls, view controls, status, results, assumptions — is appended **inside the shopping-list pane** (`:458-460`), not the left panel. Two placement decisions follow:

- **Run controls → the new right panel** (`.tab-panel-right`, sibling of `.upgrades-tab-left` inside `contentContainer`). This is the Bulk copy, and it also fixes a latent defect: Run/Stop/Import currently vanish when a slot sub-tab is active. The executor must not "helpfully" keep a copy in the pane.
- **View controls → `.upgrades-tab-left`, as a direct child rendered *before* `.upgrades-tab-tabs`** — outside every pane, so the three filters are visible and govern whichever pane is active. Leaving them inside the shopping-list pane would reproduce the exact failure this stage exists to fix (a control the owner cannot find). **Grid consequence (re-review F11):** `.tab-panel-left` is `display: grid; grid-template-columns: repeat(auto-fit, minmax(220px, 1fr))` (`_sim_tab.scss:19-27`, C28). Today the panel has exactly one direct child, so the grid renders as one column; a second direct child makes `auto-fit` place the view-controls row **beside** the sub-tab area at any width fitting two 220px tracks — the very misplacement this move exists to fix. Containment: the view-controls row gets `grid-column: 1 / -1` in `_upgrades_tab.scss` so it spans a full grid row above the tabs. Chosen over wrapping both children in a `.tab-panel-col` because it adds one local CSS rule with no DOM wrapper, and below the `lg` breakpoint — where `_sim_tab.scss` switches the panel to flex-column — `grid-column` is inert, so the narrow-width stacking is preserved by construction rather than by a new wrapper's behaviour. `_sim_tab.scss` is shared with every other tab and stays unedited.

The status line, results, and assumptions stay inside the shopping-list pane (slot panes have their own content; nothing about them moves).

**Pickers are the real mechanism, not a markup imitation.** `BooleanPicker`/`EnumPicker`/`NumberPicker` extend `Input<ModObject, T>` with no `Sim`/`Player` constraint (`ui/core/components/input.tsx:11-44`), and Bulk already binds them to plain component state: `new BooleanPicker<BulkTab>(div, this, {...})` with `changedEvent: _modObj => this.settingsChangedEmitter`, a bare `TypedEvent<void>` field (`bulk_tab.tsx:47, 667-818`). `UpgradesTab` does the same. The one exception is the Phase selector: `makePhaseSelector` (`other_inputs.ts:77-91`) is a `Sim`-bound `EnumPicker` deliberately surfacing the page's shared phase (`upgrades_tab.tsx:588-592`) — it moves as-is, never converted to tab-owned state. Per review F5 the picker conversion is split into its own slice (2b), because it changes *when* values are read: today `readCandidateCap()` re-derives at Run-click time (`:678/:685-687/:787`), while a picker writes through on change — 2b must preserve the read-at-click semantics (pickers update tab state; the Run handler still derives the cap at click).

**The known silent SCSS break this plan defuses explicitly (review F6 sharpened it).** The toolbar SCSS keys rules two ways. `_upgrades_tab.scss:17-24` nests `.upgrades-run-controls, .upgrades-view-controls` **inside** `.upgrades-toolbar` (flex-wrap, gap, row-gap) — those rules stop applying the moment either row leaves the toolbar ancestor, with no error. The top-level block starting at `:45` is **interleaved**: its inner selector lists mix run-row and view-row children (`.upgrades-iterations-label` beside `.upgrades-set-potential-label`, `:45-100`). So the split is a **de-interleaving per child selector** — each child selector is assigned to exactly one new parent scope — not a duplication of one selector list. Additionally, the picker conversion (2b) deletes `.upgrades-iterations-label` / `.upgrades-candidates-label` from the DOM, so their rules go dead and are removed in 2b, and the `8ch` clip measurement (C26) is taken against the **new picker element**, not the old rule. Each moving slice carries a countable check (`grep -c` of the class names in the SCSS with an expected count) plus a gap/wrap screenshot.

Rejected alternative: keeping everything in place and only regrouping rows (direction A). It lost because the owner chose C, and because the card gives the label-wrap and Run-primacy fixes structurally instead of via per-row CSS surgery.

One deliberate divergence from a literal Bulk copy: the running state stays on the inline status line (`upgrades_tab.tsx:529-561` — the live-region machinery is deliberate and commented); no progress modal. And the view controls move to the left panel above the panes, which Bulk has no equivalent for (its results are not post-filterable) — a flagged divergence, not a false borrow.

**Formatter reuse caveat (tickets since corrected to match):** `firstLineOf`, `wowsimsItemIdsJson`, `formatSetPotentialLine`, and `SET_POTENTIAL_WEIGHTS` live in the main repo's `packages/core/src/rank-report*.ts` and are **not present anywhere in the fork's `ui/`** (C7). The tab cannot import them, and the engine port dir is byte-gated, so they are re-implemented locally in `upgrades_tab.tsx` (each under ten lines), with a comment naming the report-path original — the same "deliberate drift" pattern already used at `upgrades_tab.tsx:1840-1852`. `SET_POTENTIAL_WEIGHTS` does **not** apply on this surface: the fork's view ranks on raw `prospectiveBonusDps` (`view.ts:169-172`) and the row displays raw `deltaDps` (`:1606`), so the number ticket 313 shows is the raw prospective bonus, which reconciles exactly with what the toggle adds to the sort — no discount, and none must be claimed.
