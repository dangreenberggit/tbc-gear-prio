# Plan — stage-3-web-shell (revision 1)

## Goal

When this plan is done, `apps/web` is a workspace package containing one Node 22 process that serves three routes (`/`, `/c/$region/$realm/$name`, `/run/$id`) and a JSON API (`POST /api/jobs`, `GET /api/jobs/:id`, `GET /api/characters/:region/:realm/:name`, two export endpoints). The server runs `rankUpgrades` from `@tbc-gear-prio/core` through the **same offline wiring the CLI uses** (`RecordedGearSource` + `CliSimRunner` + `MemoryStore`, or `SqliteStore` when `DATABASE_URL` is set), with an in-process worker that stores honest progress derived from `rankUpgrades`' `Progress` events. The React SPA renders skeleton rows once the candidate count is known, fills them as `kind: "row"` events arrive, never re-sorts during a run, re-sorts once (animated) at completion, and re-renders every view control through `applyView` in the browser — from a `@tbc-gear-prio/core/view` entry whose bundle does not contain `data/items/index.json` — with no network call. The results page has an assumptions drawer, a below-cutoff expand, a hit-cap banner with `hitDriven` marks, a pin-BiS control that is absent when `pinBisAvailable` is false, a wowsims attribution footer with the pinned sim version, an `IndividualSimSettings` JSON download and a wowsims share link that `wowsimcli decodelink` round-trips with the correct `apiVersion`. `pnpm verify` is green on the tip and covers `apps/web`. `docs/verification-log.md` has a dated Stage 3 entry that closes five gate boxes with commands and records the first box (`type a character`) open pending the live-source ticket. Tickets 72 and 78 are re-blocked or closed with reasons; the live `WclGearSource` work is a new `Blocks: phase-3` ticket. Every Stage 1 CLI test passes unchanged. Nothing is merged to `dev`.

## Approach

**Chosen:** an offline-first shell (`Q1 = A`), built as one Node server app plus a Vite-built React SPA in `apps/web` (`Q2 = A`), export-only codec with both halves written in core (`Q3 = A`), `MemoryStore` by default with `SqliteStore` as a `DATABASE_URL` opt-in (`Q4 = B with opt-in`). The CLI's adapter composition is **moved** into `packages/core/src/cli-wiring.ts` and called from both `cli.ts` and the server, so the web wiring is shared, not copied.

**Deviations from §12 and the brief, stated up front:**

1. `POST /api/jobs` cannot dedupe on `contentHash` at submit time — `contentHashOf` runs inside `rankUpgrades` after gear is read (C10). The server dedupes in-flight jobs on `submitKey` (canonical JSON of the `RankInput`); cross-run dedupe is `rankUpgrades`' own ranking cache keyed by `contentHash` in the `Store` (C10). The job record carries `contentHash` once the run has it.
2. The `/c/...` route is offline: it resolves the three recorded characters (C6) and returns 404 `not a recorded character (offline build)` otherwise.
3. **TMB's control labels are not confirmed** (C25). `thatsmybis.com` and `/help` return marketing and FAQ text without control labels, and a live guild view needs a login. The UI ships §12's table wording (Raid, Boss, Group by slot, Already have it, Pin BiS); renaming later is a string change. The log entry records the two URLs tried.
4. Skeleton rows are rendered when the candidate count is known, not at submit. `Progress` carries `total` as sims (baseline + candidates + replicas, C33), not rows, so step 2c adds an optional `candidates` field to the first `simming` event. Before that event the list area is a fixed-height container, so nothing shifts; at completion, candidates that produced no row (`rank.ts:965` `if (!best) return`) are removed in the single permitted animated re-sort.
