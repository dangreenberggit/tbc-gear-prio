# Plan — stage-3-web-shell

## Goal

When this plan is done, `apps/web` is a workspace package containing one Node 22 process that serves three routes (`/`, `/c/$region/$realm/$name`, `/run/$id`) and a JSON API (`POST /api/jobs`, `GET /api/jobs/:id`, `GET /api/characters/:region/:realm/:name`). The server runs `rankUpgrades` from `@tbc-gear-prio/core` through the **same offline wiring the CLI uses** (`RecordedGearSource` + `CliSimRunner` + `MemoryStore`, or `SqliteStore` when `DATABASE_URL` is set), with an in-process worker that stores honest progress derived from `rankUpgrades`' `Progress` events. The React SPA renders skeleton rows up front, fills them as `kind: "row"` events arrive, never re-sorts during a run, re-sorts once (animated) at completion, and re-renders every view control through `applyView` in the browser with no network call. The results page has an assumptions drawer, a below-cutoff expand, a hit-cap banner with `hitDriven` marks, a pin-BiS control that is absent when `pinBisAvailable` is false, a wowsims attribution footer with the pinned sim version, an `IndividualSimSettings` JSON download and a wowsims share link that `wowsimcli decodelink` round-trips. `pnpm verify` is green on the tip and covers `apps/web`. `docs/verification-log.md` has a dated Stage 3 entry that closes five gate boxes with commands and records the first box (`type a character`) as open pending the live-source ticket. Tickets 72 and 78 are re-blocked with reasons; the live `WclGearSource` work is a new `Blocks: phase-3` ticket. Every Stage 1 CLI test passes unchanged. Nothing is merged to `dev`.

## Approach

**Chosen:** an offline-first shell (`Q1 = A`), built as one Node server app plus a Vite-built React SPA in `apps/web` (`Q2 = A`), export-only codec with both halves written in core (`Q3 = A`), `MemoryStore` by default with `SqliteStore` as a `DATABASE_URL` opt-in (`Q4 = B with opt-in`). The CLI's adapter composition is **moved** into `packages/core/src/cli-wiring.ts` and called from both `cli.ts` and the server, so the web wiring is shared, not copied.

**Answers to the brief's four questions** (candidate → pre-stated win condition → measurement → result):

- **Q1.** A wins by default. Measurement: `ls .env` at the worktree root returns "No such file" (C1), so `WCL_CLIENT_ID` is not available and B cannot be verified here. B is dropped for that reason alone; its size (§5.2 lists OAuth, two GraphQL routes, spec classification, `rateLimitData`, retry, recorder, plus R9's TTL and rate limit) would also be the largest single slice of this plan. A's cost: the first gate box cannot close in this plan; it is recorded open, with the new live-source ticket (`Blocks: phase-3`) named in the log entry.
- **Q2.** A wins. Measurement by the Paths manifest: A adds 3 runtime deps (`react`, `react-dom`, `@tanstack/react-query`) and 4 dev deps (`vite`, `@vitejs/plugin-react`, `@types/react`, `@types/react-dom`); server is `node:http` + `node:zlib` + `node:sqlite`, zero server deps. Glue outside `packages/core` is the server (~5 files) and the SPA (~12 files). The `rankUpgrades` wiring is shared via `cli-wiring.ts` (step 2), not copied. B (TanStack Start / Remix / Next) is dropped: each installs a framework runtime and a bundler integration on top of React for three routes and one poll endpoint — the dependency count is strictly larger than A's 7 and removes no code we write, because the API handlers and the job worker are ours either way (`hypothesis, untested` on exact counts; A's 7 is the plan's number).
- **Q3.** A wins. The share-link codec is `IndividualSimSettings.toBinary → zlib deflate → base64 → URL hash`, and the importer is its exact inverse (C9). Both halves are ~15 lines each and share nothing with ticket 72's `IndividualSimSettings → RaidSimRequest` lift; the export needs the **opposite** lowering (`RaidSimRequest → IndividualSimSettings`, step 3). So building the export does not duplicate 72's lift. The codec module ships both `encodeShareLink` and `decodeShareLink` (the decode half costs one unit test and gives 72 its Stage 2 for free). 72 is re-blocked to Stage 5 with that reason (step 14). Measurement: `wowsimcli decodelink <link>` exit 0 and JSON equal to the exported settings (step 3 acceptance).
- **Q4.** B wins on the brief's measurement: none of the six Stage 3 boxes needs state to survive a restart — each is evidenced within one server session (the box list in PLAN.md §14 L909 names no restart; "caches survive restart" is Stage 4 L915, C3). `MemoryStore` is the default and the test store. `SqliteStore` is still wired as a one-line opt-in behind `DATABASE_URL` (§13 names the variable), which gives ticket 78 a real call site for `SqliteStore`. `CachingGearSource` needs a live inner source and is re-blocked to the live-source ticket. Ticket 31's race does not affect this shell: `SqliteStore.job.create` runs `SELECT COUNT(*)` and `INSERT` synchronously on `DatabaseSync` with no `await` between them (C12), and one server process is the only writer; the delete-wedge does not arise because nothing deletes jobs.

**Strongest rejected alternative:** Q1-B, building `WclGearSource` here so the first gate box closes in-plan. It lost on a hard fact (no credential, C1) — not on taste. If a credential appears, the follow-up ticket is the place, and nothing in this plan has to be undone: the server takes its `GearSource` through the `Deps` object, so the live adapter is a composition change in `apps/web/server/wiring.ts` only.

**Two deviations from §12, stated up front:**

1. `POST /api/jobs` cannot dedupe on `contentHash` at submit time, because `contentHashOf` is computed inside `rankUpgrades` after gear is read (C10). The server dedupes in-flight jobs on a `submitKey` (canonical JSON of the `RankInput`), and **cross-run** dedupe is `rankUpgrades`' own ranking cache keyed by `contentHash` in the `Store` (C10), so a resubmission after completion returns the cached ranking in one `onProgress` burst. The job record carries `contentHash` once the run has it. This is recorded in the log entry as a deviation with the reason.
2. The `/c/...` route is offline: it resolves only the recorded characters (C6) and returns 404 with the message `not a recorded character (offline build)` for anything else. The live version is the follow-up ticket.
