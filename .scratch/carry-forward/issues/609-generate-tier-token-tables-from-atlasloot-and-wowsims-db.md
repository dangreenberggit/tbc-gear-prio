# Generate the tier-token tables instead of writing them by hand

A feral player at phase 5 never sees three Thunderheart pieces as
candidates: Thunderheart Wristguards (34444), Thunderheart Waistguard
(34556) and Thunderheart Treads (34573). They are absent from
`data/universes/feral-p5.json` (481 entries). Every other spec's list has
its 3 Sunwell tier pieces.

## The owner's words, 2026-10-11

On the cause: "These are tier items like any other so many it has to do
with the sources--> tier token -->tier vendor --> tier item system"

On the fix: "It's kind of yikes that this was missed, and even more yikes
that it needs to be added manually. There should be a programmatic way to
check and add such items (for example if we add more specs)"

## Why the pieces are missing

- `scripts/assemble_universe.py` keeps an item only if it finds a source or
  another route admits it (`:2661-2663`, `:2693-2730`). The wowsims item
  database has all three pieces at phase 5 with `setId` 676 but no
  `sources`, and does not contain the Sunwell tokens 34852, 34855 or 34858
  at all. So a tier piece gets its source only from the hand-written token
  table, `data/two-hop/<spec>-tokens.json`.
- `data/two-hop/feral-tokens.json` has no rows for the three Sunwell
  tokens; its third note (`:12`) says they were left out on purpose.
  `data/two-hop/balance-tokens.json:147-173` maps the same tokens for
  balance, so the token grouping is known.
- The hand-written `*_TIER_PIECE_IDS` constants
  (`scripts/assemble_universe.py:189-499`, one per spec) list each spec's
  tier pieces again. `FERAL_TIER_PIECE_IDS` (`:216-229`) has only T4 and
  T5 ids, so the pool report that uses it does not show the T6 gap.

## What a prototype showed (2026-10-11)

A throwaway prototype (`gen_tokens.py` in a session scratchpad, may be
gone) built every spec's token table from `vendor/atlasloot/data-tbc.lua`
(the `T4_SET`, `T5_SET` and `T6_SET` tables and the token rows) joined to
`vendor/wowsims/db.json` `setId`:

- AtlasLoot tier-set rows: T4 17, T5 17, T6 17; 54 token rows parsed.
- It reproduced all 195 existing token rows across the 11 specs (195
  match, 0 differ, 0 missing) and added feral's 3 Sunwell rows
  (34852 → 34444, 34855 → 34556, 34858 → 34573, Kalecgos, Brutallus and
  Felmyst).
- It needed one hand-written table that cannot be read from either
  source: which classes each of the 6 token groups is for. It affects only
  each row's `tokenId` and name.

## What would close this

1. The token tables in `data/two-hop/*-tokens.json` are generated by
   `scripts/parse_atlasloot.py` (or a script it calls) from AtlasLoot and
   the wowsims database, and `pnpm atlasloot:regen:check` fails when a
   committed table differs from a regen. The 6-row token-group → classes
   table is the only hand-written input, with its reason written beside
   it.
2. The `*_TIER_PIECE_IDS` constants are derived from the same data, or
   removed, so no spec's tier list can be shorter than its token table.
3. `data/universes/feral-p5.json` (and the fork copy) contains 34444, 34556
   and 34573, and every other spec's universe is byte-identical or its
   diff is explained in the closing note.
4. `pnpm verify` rc=0.

## Closed 2026-10-16 (stage-gate tab-blocking-finish, K4)

The token maps are generated. `scripts/generate_tier_tokens.py` writes
`data/two-hop/<spec>-tokens.json` and `data/two-hop/tier-sets.json` from
AtlasLoot and the wowsims database (7e682fc1); `data/two-hop/token-groups.json`
is the only hand-written input, and its note says why.
`pnpm atlasloot:regen:check` regenerates and byte-compares them. The
`*_TIER_PIECE_IDS` constants are removed; the builder reads tier pieces from
the token maps (35f7f82c). `data/universes/feral-p5.json` and its fork copy
hold 34444, 34556 and 34573, and the token check in
`packages/core/test/pool-hardening.test.ts` loops over `tier-sets.json` for all
11 specs (d74d5fcc). Ticket 298, which this closes, is already closed.

(prints nothing) at tbc-gear-prio@808f0c7f; `pnpm verify` rc 0 on the close
commit.
