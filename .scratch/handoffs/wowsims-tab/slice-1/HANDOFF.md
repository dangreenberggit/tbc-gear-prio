### The fnm trap — read this before running anything in the fork

The fork carries `.nvmrc` = `22.17.1`. Every command run from a shell whose cwd
is inside the clone tripped:

```
error: We can't find the necessary environment variables to replace the Node version.
```

Two things were true at once, and fixing only one does not work:

1. **The pinned version was not installed** (machine had 22.16.0). Fixed with
   `fnm install 22.17.1`.
2. **This harness's non-interactive shells never run `fnm env`**, so the fnm
   shim on `PATH` has no `FNM_MULTISHELL_PATH` and fails closed. Prepending a
   real Node directory does *not* fix it, because `protoc-gen-ts.cmd` re-resolves
   `node` through `PATH` and finds the broken shim again.

**The working recipe** — start every fork shell with this:

```bash
eval "$(fnm env --shell bash)"
export PATH="$FORK/node_modules/.bin:$PROTOC_BIN:/c/Program Files/Go/bin:/c/Users/dgree/go/bin:$PATH"
```

`fnm env` provisions a multishell dir and auto-switches to 22.17.1 on `cd`.

### npm, not pnpm — and `--prefix`, not `cd`

The fork uses **npm** (`package-lock.json`); this repo's pnpm is irrelevant
inside it. Because `cd`-ing in tripped the fnm error before npm ever ran, the
install that worked was driven from outside the tree:

```bash
node npm-cli.js ci --prefix "<fork path>" --no-audit --no-fund
```

→ `added 559 packages`, exit 0. Once `fnm env` is evaluated, an ordinary
`npm ci` inside the tree works too.

## Why no dispatched worker

orchestrator seat did the clone/branch/preflight directly because the work up
to this point is a handful of git and version commands, and the toolchain gap
needed a user decision mid-stream — a worker would have hit the same wall and
handed it straight back. The **build + tab-registration** portion of slice 1
is still worker-shaped and gets dispatched once the toolchain is verified.
